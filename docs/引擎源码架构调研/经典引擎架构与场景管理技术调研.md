## 2. Quake / id Tech 1（1996）

### 2.1 目录结构（实测 626 文件）

```
QW/                ← 客户端 + 专用服务器（模块化，193 client 文件）
  client/          ← 纯客户端：cl_*(状态/预测/解析) gl_*(渲染) r_*(软件渲染)
                    pmove.c pmovetst.c  ← 玩家移动，独立成文件
                    zone.c             ← zone/hunk/cache 三层
  server/          ← sv_*(实体/物理/发送) world.c pr_cmds.c pr_exec.c
  progs/           ← 编译好的 QuakeC
WinQuake/          ← 单机版单体（WinQuake.exe），r_*软件渲染 + gl_*OpenGL 双份
qw-qc/             ← QuakeC 源码（world.qc client.qc combat.qc items.qc ...）
```

对比：`WinQuake/` 是「一个 exe 全都塞进去」的 1996 年形态；`QW/` 才是**真正的模块化重构**（client 与 server 可各自独立编译）。这是 id 第二次自我重构，比第一次（Doom 单体）进步显著。

### 2.2 核心子系统与关键文件

|---|---|---|

| 命令解析 | `cmd.c` | `COM_Tokenize_Parse` 文本 tokenizer（**注意：id Tech 1 用的是 if-else 链，不是 jump table**） |

| PVS 消费（AI） | `pr_cmds.c` | `PF_checkclient`：目标不在 PVS 内直接返回 nil |

| 脚本 VM | `pr_exec.c` | QuakeC 字节码 `switch(st->op)` 解释执行 |

### 2.3 值得继承的架构决策

**（1）`pmove.c` 的纯函数化——移动逻辑三处复用**

`PMove` 不碰任何全局状态，输入是 `player_state_t* from` + `usercmd_t`，输出写进 `player_state_t* to`。因此同一份 `.c` 文件可以直接编进三个地方：
- 服务端 `sv_phys.c`（权威模拟）
- 客户端 `cl_pred.c`（预测）
- 录像回放 `cl_demo.c`

这是**接口层面的单一真理源**：作弊者拿到的客户端与服务器跑完全相同的物理。代价是 `moveclip_t` 这种结构体要显式贯穿传参，比"用全局变量方便写"要啰嗦。

**（2）PVS 是「保守并集」而非「精确可见」——`SV_AddToFatPVS` 的 8 单位 magic number**

实测代码（`QW/server/sv_ents.c`）：
```c
plane = node->plane;
d = DotProduct (org, plane->normal) - plane->dist;
if (d > 8)          node = node->children[0];
else if (d < -8)    node = node->children[1];
else { /* go down both */ SV_AddToFatPVS(org, node->children[0]); node = node->children[1]; }
```
注释写得很直白：`Calculates a PVS that is the inclusive or of all leafs within 8 pixels of the given point`（原注释说 pixels，实际是 8 world units 的 sloppy 经验值）。

**为什么这么做**：PVS 的消费者是「要不要画这个面」——**假阳性的代价是多画几个三角形（视觉浪费），假阴性的代价是墙穿帮（bug）**。所以宁可多画。当 PVS 恰好切到 portal 上时，不做保守膨胀就会漏掉透过门缝看到的房间。

这个**非对称代价驱动的保守性选择**，是所有可见性系统的通用原则：PVS 保守（少剔除多画），shadow map / Hi-Z 也必须保守。

**（3）`R_MarkLeaves` 的 visframecount 打戳——零内存的可见性传播**

实测（`QW/client/r_main.c`）：
```c
vis = Mod_LeafPVS (r_viewleaf, cl.worldmodel);
for (i=0 ; i<cl.worldmodel->numleafs ; i++) {
    if (vis[i>>3] & (1<<(i&7))) {
        node = (mnode_t *)&cl.worldmodel->leafs[i+1];
        do {                       // 沿 parent 回溯到根，标记所有祖先
            if (node->visframe == r_visframecount) break;   // 已标记则剪枝
            node->visframe = r_visframecount;
            node = node->parent;
        } while (node);
    }
}
```
三点设计精髓：
1. **只存一份 vis 位图**，不存「可见节点列表」。存储从 O(可见节点数) 降到 O(numleafs/8) —— Quake 典型关卡 numleafs ≈ 1000，即 125 字节。
2. **`visframecount` 单调递增整数**替代「每帧清空标记数组」。省掉 O(n) 清零，且天然免疫「上一帧残留导致本帧误判」。
3. **回溯时遇已标记即 break** —— 一个节点被标记一次后，其所有祖先必然已被标记（这由回溯的完整性保证），所以剪枝是正确的。这让总复杂度从 O(可见叶 × 树深) 降到 O(可见叶 + 树节点数)。

这个模式在 30 年后仍原样出现在现代引擎里（UE 的 `bVisible`，Unity 的 `Renderer.isVisible`）。

**（4）zone / hunk / cache 三层分配器——按「生命周期」而非「大小」分类**

实测 `zone.c` 有两种完全不同的分配器：
- **zone（`Z_Malloc`）**：真正带 `memblock_t` 头（`size/tag/id/next/prev`）的双向链表，带空闲块合并与 `Z_CheckHeap` 一致性校验。**唯一 API 是 `Z_Free(ptr)`——按指针释放，没有按生命周期批量释放。**
- **hunk（`Hunk_AllocName`）**：只从 `hunk_low_used` 单向水位线往上分配，**只能按 `Hunk_FreeToLowMark(mark)` 逆序批量释放**。头只有 12 字节（`sentinal/size/name[8]`），`name` 字段是给调试器看的——泄漏时能直接打印是哪个子系统占的。

**为什么这么分**：1996 年的瓶颈不是 malloc 慢，而是**「关卡切换时如何一次性回收所有东西」**。hunk 的 mark/release 正好匹配「加载一个关卡 → 释放 → 加载下一个」这个节奏，比逐个 free 快 O(1)，且不可能忘记释放某个块。现代引擎的 `Arena`/`Pool`/`ResourceHeap`（UE4/5 的 `FResourceArray`、Vulkan 的 `DescriptorPool`）是同一个思路。

注意 `hunk_t` 里的 `HUNK_SENTINAL = 0x1df001ed` 校验和 `memblock_t.id = ZONEID` —— 这种「魔法哨兵值 + 释放时校验」是 90 年代防御野指针 free 的标准手法，现代引擎用 ASan/内存消毒器替代了它，但**批量释放的思想留下来了**。

**（5）QuakeC 字节码 VM——逻辑与引擎解耦的双刃剑**

实测 `pr_exec.c`：`char *pr_opnames[]` 列出全部操作码，解释器是巨型 `switch (st->op)`，其中 `case OP_ADD_V: c->vector[0] = a->vector[0] + b->vector[0]; ...` 这种形态正是「字节码 + 直接 switch 派发」的教科书实现（**不是** jump table —— 任务描述里的 "fast function pointer / COM_Tokenize_Parse 的 jump table" 在 id Tech 1 中不成立，`cmd.c` 是文本 tokenizer，`pr_exec.c` 是 switch；跳板表是更后期 id Tech 的优化）。

**权衡**：把怪物 AI、物品逻辑、关卡触发器做成可热替换的数据，modder 不需要重编译整个引擎 → 催生了 enormous 的 mod 生态。但代价是：每次 AI 调用都要穿越 C→VM 边界（参数压栈、`OP_CALL` 压返回地址），性能远低于原生代码，且**任何 VM bug 都可能变成远程代码执行漏洞**（这也是 id 后来弃用 QuakeC、转向原生实体脚本的原因）。

**（6）`PF_checkclient`——PVS 同时驱动 AI 感知**

实测 `pr_cmds.c`：
```c
leaf = Mod_PointInLeaf (org, sv.worldmodel);
pvs = Mod_LeafPVS (leaf, sv.worldmodel);
memcpy (checkpvs, pvs, (sv.worldmodel->numleafs+7)>>3);
```
把目标玩家的 PVS 快照存下来（`checkpvs` 是 `usercmd` 级的缓存，每 0.1 秒刷新一次），后续每帧判断「我是否在目标的 PVS 内」。

**关键洞察**：PVS 不只服务渲染。它同时是**游戏性的可见性判据**（敌人能否发现我），且必须与服务端权威一致。现代引擎里这条路径分裂成了"渲染可见性"（GPU 侧）和"感知可见性"（CPU 侧、要做 LOS raycast + 视野 FOV + 遮挡掩体），但概念相同。

### 3.2 核心机制

**（1）WAD lumps——资源即数据，代码永不解析资源格式**

实测 `p_setup.c`：
```c
numsectors = W_LumpLength (lump) / sizeof(mapsector_t);
sectors = Z_Malloc (numsectors*sizeof(sector_t), PU_LEVEL, 0);
ms = (mapsector_t *)data;
for (i = 0; i < numsectors; i++, ss++, ms++) { ss->plane = SHORT(ms->plane); ... }
```
WAD 是一个「lump 名 → 偏移」的平铺索引表，引擎只认 lump 编号（`ML_SECTORS` 等），格式解析与引擎逻辑彻底解耦。

**价值**：这份解耦让 Doom 的社区生态极度繁荣——DeHackEdits（`deh_*.c` 系列）可以直接改写引擎行为而不动引擎代码。**这就是「数据驱动」的第一次完整实现**，比 Quake 的 QuakeC 更底层也更灵活。

**（2）blockmap——128×128 世界单位的均匀网格**

实测 `p_setup.c`：
```c
blockmaplump = W_CacheLumpNum (lump, PU_LEVEL);
blockmap = blockmaplump + 4;
bmaporgx = blockmaplump[0] << FRACBITS;
bmapwidth = blockmaplump[2]; bmapheight = blockmaplump[3];
```
`p_map.c` 的碰撞遍历：
```c
xl = (tmbbox[BOXLEFT]   - bmaporgx) >> MAPBLOCKSHIFT;
xh = (tmbbox[BOXRIGHT]  - bmaporgx) >> MAPBLOCKSHIFT;
for (bx = xl; bx <= xh; bx++)
  for (by = yl; by <= yh; by++)
    if (!P_BlockThingsIterator(bx, by, PIT_CheckThing)) return false;
```

**设计权衡**：均匀网格（uniform grid）vs BSP：
- 均匀网格 **O(1) 定位、无需深度平衡、构建时间 O(n)、缓存友好**；
- 但**在空旷区域浪费格子，在密集区域格子不够用**（需要链式溢出，Doom 的 blockmap 单元存的是链表头指针）；
- BSP 适合**静态几何的精确剖分**，但要花离线时间构建，且负载不均时退化。

Doom 关卡是「走廊 + 房间」的密闭拓扑（无开阔地形），均匀网格是完美匹配。**如果让 Doom 渲染一片 10km 平原，blockmap 会爆炸** —— 这正是 Quake 转向 BSP 的原因之一。

**（3）`R_CheckBBox` 的八分象限查表 —— GPU-driven culling 的思想祖先**

实测 `r_bsp.c`：
```c
int checkcoord[12][4] = {
    {3,0,2,1}, {3,0,2,0}, {3,1,2,0}, {0},
    {2,0,2,1}, {0,0,0,0},
    {2,0,3,1}, {2,1,3,1}, {2,1,3,0}
};
boolean R_CheckBBox (fixed_t *bspcoord) {
    boxx = viewx <= bspcoord[BOXLEFT]  ? 0 : (viewx < bspcoord[BOXRIGHT] ? 1 : 2);
    boxy = viewy <= bspcoord[BOXBOTTOM]? 0 : (viewy < bspcoord[BOXTOP]   ? 1 : 2);
    boxpos = boxx + boxy*3;
    ...
    for (i=0 ; i<4 ; i++) {
        switch (checkcoord[boxpos][i]) {   // 查表 + 分支，无算术
        case 0: continue;
        case 1: angle1 = ct[r]  - vangle; break;
        ...
        }
    }
}
```
**为什么用查表 + switch 而不是算术**：在 486 上算术指令慢，Doom 把「视点位于包围盒 3×3 网格的哪一格」映射成「用哪 4 个角算哪 4 个角度」，预先把 9 种情况的 12 个角索引编成常量表。这与 2020 年代 GPU-driven culling 里「用 compute shader 预先算好分类表」是同一思路：**把分支密集的几何判断预编译成查表**。

Doom 只有 X 轴 3×3 = 9 种情况（因为 Doom 是 2.5D，只有 Y 轴判定 + 前后）。表里有些行是 `{0}`（只需 1 个角）或 `{0,0,0,0}`（无需判定，直接返回），全靠预计算剪枝。

**（4）`Z_Malloc(size, tag)` + `Z_FreeTags(PU_LEVEL)` —— 流送内存管理的直系祖先**

实测 `z_zone.h`：
```c
#define PU_STATIC       1   // static entire execution time
#define PU_SOUND        2   // static while playing
#define PU_MUSIC        3
#define PU_DAVE         4   // anything else Dave wants static
#define PU_LEVEL       50   // static until level exited
#define PU_LEVSPEC     51   // a special thinker in a level
#define PU_PURGELEVEL 100   // ← 可按需 purge
#define PU_CACHE       101
```
`z_zone.c` 的 `Z_FreeTags(lowtag, hightag)` 遍历全局块链表，批量释放落在 tag 区间内的所有块。

**这就是资源流送的全部机制**：`p_setup.c` 里所有 `PU_LEVEL` 分配（sectors/nodes/lines/blockmap/vertices）都是「关卡生命周期」，`Z_FreeTags(PU_LEVEL, PU_LEVSPEC)` 一次调用就把整个关卡的内存还回系统 —— 无论有多少块、什么顺序分配的。

**现代对应**：
- UE5 的 `LLM`/`Malloc` + `FScopeLock` 不做这个；World Partition 用的是「Actor 生命周期」而非「内存 tag」
- 但 Unity/自定义引擎里 `Tag` + `FreeTag` 依然是最实用的批量回收手段
- Vulkan 的 `DescriptorPool`（`vkResetDescriptorPool` 一次清空）、wgpu 的 `BindGroupLayout` 都遵循「按生命周期而非按对象」的分池原则

**关键教训**：`PU_PURGELEVEL = 100` 注释是 `purgable whenever needed` —— 这是**内存压力驱动的主动驱逐**的最早形态。现代引擎的 streaming pool eviction（如 Nanite 的 resident page 淘汰、texture streaming 的 budget）本质相同。

### 3.3 值得继承的决策

1. **数据（lump）与代码严格分离**，让 mod 生态可以不改引擎就改变行为。
2. **内存按生命周期分池 + 批量释放**，比逐个 free 更快且不可能漏。
3. **剔除决策预编译成查表**，把运行时分支换成常量访问。
4. **固定点整数（16.16 fixed point）**：无 FPU 的机器上把浮点转成 `int16 + int16 frac`，`FRACBITS=16`。现代引擎已全部回到 float/half，但移动端与主机仍保留定点 SIMD 路径。

#### 4.2.2 `cNode_t` —— 教科书级 BVH（实测 `cm_local.h`）

```c
typedef struct {
    cplane_t *plane;
    int       children[2];   // negative numbers are leafs
} cNode_t;
```
三个设计点：
1. **`children[2]` 二叉而非多叉**：渲染和物理遍历都极简单。代价是树深 ≈ log2(n)，比 4/8 叉多约 1-2 层。
2. **负数编码 leaf 索引**（`-leaf - 1`）：省掉一个 `type` 字段 + 省掉一个分支预测失败。**空间换分支预测** —— 碰撞检测是分支密集型，这个交换极划算。
3. **`cLeaf_t` 同时含 brush 与 surface 区间**：`firstLeafBrush/numLeafBrushes`（给物理）+ `firstLeafSurface/numLeafSurfaces`（给渲染）。**一个 leaf，一次遍历，两种用途** —— 这是「碰撞与渲染数据分离但共享空间划分」的关键。

#### 4.2.3 area portal 的引用计数与增量洪泛（实测 `cm_test.c`）—— **Portal culling 的真正形态**

```c
void CM_AdjustAreaPortalState( int area1, int area2, qboolean open ) {
    if ( open ) {
        cm.areaPortals[area1 * cm.numAreas + area2]++;
        cm.areaPortals[area2 * cm.numAreas + area1]++;
    } else {
        cm.areaPortals[area1 * cm.numAreas + area2]--;
        cm.areaPortals[area2 * cm.numAreas + area1]--;
        if ( ... < 0 ) Com_Error( ERR_DROP, "...negative reference count" );
    }
    CM_FloodAreaConnections();       // ← 每次 portal 开关都重算连通性
}
void CM_FloodAreaConnections( void ) {
    cm.floodvalid++;                 // ← 版本号 +1，所有旧 flood 标记失效
    floodnum = 0;
    for (i = 0; i < cm.numAreas; i++) {
        if (cm.areas[i].floodvalid == cm.floodvalid) continue;  // 已灌过
        floodnum++;
        CM_FloodArea_r(i, floodnum);
    }
}
```

**三个关键设计**：
1. **`areaPortals` 是 N×N 稠密矩阵存引用计数**，不是 portal 邻接表。N 通常只有几十到几百（Q3 单关卡约 32-64 个 area），N² = 4096 个 int 完全可以承受，换来 O(1) 查询「area1 和 area2 是否连通」+ **天然支持多个 portal 连接同一对 area**（引用计数 > 1）。
2. **`floodvalid++` 版本号而非逐个清标记** —— 与 Quake 的 `visframecount` 完全同源，都是「单调计数代替清零」。
3. **`Com_Error` 检查负引用计数** —— portal 开关配对错误的开发期断言。id 对 portal 调试有一整套 `+showportals` / `+r_showportals` 的调试可视化。

**`CM_AreasConnected` 的用途**：怪物 AI 的目标筛选 —— 「我能直接走过去吗」比「我能看见吗」更严格（要绕路）。这是 portal culling 的**游戏性应用**，比 Quake 的 PVS 更进一步。

#### 4.2.4 可见性数据的加载与回退（实测 `cm_load.c`）—— **工程完备性的典范**

```c
void CMod_LoadVisibility( lump_t *l ) {
    len = l->filelen;
    if ( !len ) {                                    // ← 关键回退
        cm.clusterBytes = ( cm.numClusters + 31 ) & ~31;
        cm.visibility = Hunk_Alloc( cm.clusterBytes, h_high );
        Com_Memset( cm.visibility, 255, cm.clusterBytes );   // 全部可见
        return;
    }
    buf = cmod_base + l->fileofs;
    cm.vised = qtrue;                                // ← 标记"有真实 vis"
    cm.visibility = Hunk_Alloc( len, h_high );
    cm.numClusters  = LittleLong( ((int *)buf)[0] );
    cm.clusterBytes = LittleLong( ((int *)buf)[1] );  // 对齐到 4 字节
    Com_Memcpy( cm.visibility, buf + VIS_HEADER, len - VIS_HEADER );
}
```
配合 `CM_ClusterPVS`：
```c
byte *CM_ClusterPVS( int cluster ) {
    if (cluster < 0 || cluster >= cm.numClusters || !cm.vised ) {
        return cm.visibility;      // 未加载 vis → 返回全 1（全部可见）
    }
    return cm.visibility + cluster * cm.clusterBytes;
}
```

**三个值得学的地方**：
1. **无 vis 数据不是错误，是合法状态** —— `vised = qfalse` 时全可见。开发中的关卡（未跑 `vis`）能正常跑，只是慢。这是「可选优化」与「必需正确性」的分离。
2. **`clusterBytes = (numClusters + 31) & ~31`** —— 每行按 4 字节（32 cluster）对齐，使得取行可以直接 `uint32` 索引而非 `uint8`，编译器能向量化。**行内布局为 SIMD 优化**。
3. **vis 数据同时给 `cm_` 和 renderer** —— `tr_public.h` 里有 `void (*SetWorldVisData)(const byte *vis)`，注释写明 `the vis data is a large enough block of data that we go to the trouble of sharing it with the clipmodel subsystem`。**同一块内存，物理和渲染零拷贝共享。**

#### 4.2.5 `REF_API_VERSION` —— 渲染器作为动态库（实测 `tr_public.h`）

```c
#define REF_API_VERSION 8
typedef struct {
    void (*Shutdown)( qboolean destroyWindow );
    void (*BeginRegistration)( glconfig_t *config );
    qhandle_t (*RegisterModel)( const char *name );
    qhandle_t (*RegisterShader)( const char *name );
    void (*LoadWorld)( const char *name );
    void (*SetWorldVisData)( const byte *vis );
    void (*RenderScene)( const refdef_t *fd );
    ...
} refexport_t;
```

**这是 Vulkan / DirectX 12 的先驱** —— 用「导出一个函数指针结构体 + 版本号」定义渲染后端 ABI。客户端只依赖这个结构体，加载 `.so`/`.dll` 时检查 `version`，版本不匹配直接报错而非崩溃。

**代价**：`void (*func)(args...)` 的间接调用无法内联，每个 draw call 都有一次指针跳转 + 无法做编译期类型检查。`REF_API_VERSION` 从 1 涨到 8 说明这个 ABI 演进很慢（每加一个函数就要 bump 版本，且要处理老版本客户端）。现代引擎改为**编译期选择后端 + 虚函数表**（UE 的 `FRenderResource` 继承体系），牺牲动态切换换取零开销。

#### 4.2.6 渲染场景的「构建-提交」两段式（实测 `tr_public.h`）

```c
void (*ClearScene)( void );
void (*AddRefEntityToScene)( const refEntity_t *re );
void (*AddPolyToScene)( qhandle_t hShader, int numVerts, const polyVert_t *verts, int num );
void (*AddLightToScene)( const vec3_t org, float intensity, float r, float g, float b );
void (*RenderScene)( const refdef_t *fd );     // 之前什么都不画
```
注释直译：`a scene is built up by calls to R_ClearScene and the various R_Add functions. Nothing is drawn until R_RenderScene is called.`

**这是现代引擎 command list / render graph 的直系形态**。**为什么需要两段式**：多线程渲染时，游戏线程提交"我要画这个"，渲染线程排序后才真正提交 GPU。两段式让排序、批处理、状态预编译（避免 API call 打断流水线）成为可能。

UE4/5 的 `FRenderCommandList`、Unity 的 `CommandBuffer`、Vulkan 的 `vkCmdBind*` 序列，全部是这一模式的延续。

## 5. Cube / ET (Wolfenstein: Enemy Territory) —— 渲染器抽象（推测）

⚠️ `Xash3D/engine` 与 `et-legacy/etmain` **本次不可达**（jsDelivr files=0，路径探测全 404）。以下为推断，可验证的同构机制是第 4.2.5 节的 ioq3 `REF_API_VERSION`。

**推测的架构要点**：
- Cube 与 ET 用 **GoldSrc 引擎血统的「可插拔 renderer」**：`ref_gl`（GL）、`ref_vidgl`（GL 封装）、`ref_soft`（软件渲染）、`ref_gl3`（可编程管线）。每个 ref_* 是一个独立模块，导出 `GetRefAPI()` 返回一个 `refexport_t`。
- **`ref_gl` 是"库"而非"源码"**：Game 层只链接一个符号，用 `Sys_LoadDll` 在运行时加载具体后端。
- **CSG 刷子世界继承自 Quake 的 BSP**，但加入了「brush primitives」（轴对齐凸包 + 任意凸多边形），使引擎能编译出可视与可碰的同一表示。

**值得继承的决策（与 ioq3 同构）**：
1. **后端插件化**：一份游戏逻辑，多个渲染/音频后端（GL、Vulkan、DX、软渲）。
2. **`refexport_t` + 版本号** 作为 ABI 边界。
3. **CSG → BSP 的离线编译链**：编辑期用 CSG 布尔运算（brush 叠加/相减），编译期烘成 BSP 树，运行时零 CSG 开销。

**核心架构决策**：命名约定即架构。

- `p_`（physics/玩法）、`r_`（render）、`g_`（game）：**引擎逻辑，禁止直接调系统 API**

**这个约束如何被执行**：Chocolate Doom 能把 Doom 原版跑在 SDL、Win32、乃至现代 Wayland 上，且**不改动任何 `r_*`/`p_*` 文件**。这不是靠"约定"自觉，而是靠「所有平台差异都被 `i_*` 收敛」的结构性保证。

**tag 语义的延续**：实测 `z_zone.h` 保留了 Doom 的全部 tag（`PU_STATIC/PU_SOUND/PU_MUSIC/PU_LEVEL/PU_LEVSPEC/PU_PURGELEVEL/PU_CACHE`），20 年未变。**这是"按生命周期分池"思想稳定性的最强证据。**

**对现代引擎的启示**：任何引擎的"可移植性"最终取决于**平台差异是否被收敛在一个薄层**。Godot 的 `DisplayServer` 抽象、Unity 的 `#if UNITY_*`（失败案例——散落在业务代码里）、UE 的 `HAL/Platform` 都是同一决策的现代版本。

### 7.1 两个关键的架构决策

**（1）`components/` 按"能力"而非"层"切分**

不是 `render/` `physics/` `audio/` 这种横向分层，而是**每个组件是一个可独立测试、可被多个 app 复用的库**。`apps/opencs`（编辑器）和 `apps/openmw`（游戏）复用同一套 `components/*`。

对比：传统横向分层会导致「渲染层依赖资源层、资源层依赖工具层」的链式依赖；组件化 + 严格单向依赖（组件之间不互相依赖，只依赖 `components/misc` 的纯工具）让**每个组件可以被单独测试、单独替换**。

**（2）空间划分是「两层并存」而非「一层统一」** —— 最重要的发现

实测存在两套并行的空间索引：
- `components/terrain/quadtreeworld.{cpp,hpp}` + `quadtreenode.{cpp,hpp}` —— **四叉树**，用于地形 LOD
- `apps/openmw/mwworld/cellstore.{cpp,hpp}` —— **格子（cell）存储**，用于流送

实测 `QuadTreeNode` 的类定义（`components/terrain/quadtreenode.hpp`）：
```cpp
enum ChildDirection { NW = 0, NE = 1, SW = 2, SE = 3, Root };

class LodCallback {
    enum ReturnValue { Deeper, StopTraversal, StopTraversalAndUse };
    virtual ReturnValue isSufficientDetail(QuadTreeNode* node, float dist) = 0;
};

class QuadTreeNode : public osg::Group {
    QuadTreeNode* getParent();
    QuadTreeNode* getNeighbour(Direction dir);
    void           initNeighbours();          // 建树后统一初始化邻居指针
    void           traverseNodes(ViewData* vd, const osg::Vec3f& viewPoint, LodCallback* lodCallback);
private:
    QuadTreeNode*  mParent;
    QuadTreeNode*  mNeighbours[4];
    ChildDirection mDirection;
    osg::BoundingBox mBoundingBox;
    bool           mValidBounds;
    float          mSize;        // 以 cell 为单位
    osg::Vec2f     mCenter;
};
```

**为什么必须是两层**（这是本节的核心洞察）：

| 层次 | 数据结构 | 回答的问题 | 变更频率 |
|---|---|---|---|
| **流送层**（cellstore） | 均匀格子 / 列表 | 「这个格子的数据在不在内存里？」 | 玩家移动时**频繁变更**（秒级） |
| **LOD 层**（quadtree） | 四叉树 | 「这个格子该用哪个精度的地形？」 | 相机移动时变更（帧级） |

如果强行统一成四叉树：玩家跨格子时要在树里做**动态插入/删除 + 重平衡**，而四叉树的平衡性假设被破坏，退化成链表。
如果强行统一成格子：格子大小固定 → 要么远处格子太大浪费、要么近处格子太小导致格子数爆炸。

**`LodCallback` 抽象是关键设计**：LOD 选择策略（`isSufficientDetail` 返回 `Deeper`/`StopTraversal`/`StopTraversalAndUse`）作为回调注入，**让地形 LOD 的算法（geomorphing、误差度量、屏幕空间误差）可替换而不动四叉树结构**。这正是现代引擎 LOD 的正确形态——Unity 的 `LODGroup`、UE 的 `HLOD` 都是"可插拔策略"。

**`initNeighbours()` 的两阶段建树**：先递归建完树（有 parent/child），再单独一趟填充 4 方向邻居指针。因为邻居必然是"更高层的某个节点"，建树过程中父节点可能还不存在。**两阶段建树避免了对"向上找祖先再向下找兄弟"的重复遍历**（否则是 O(n·depth·4)）。

## 8. Cataclysm: Dark Days Ahead（现代 C++ 分层 LOD）

⚠️ 仓库**不可达**（jsDelivr 502，体积超限；raw 路径探测全 404）。以下基于官方 doxygen 文档与 Debian 源码镜像。

### 8.1 五级坐标系（官方文档实测数值）

```
overmap      180 × 180  (OMAPXxOMAPY)  ← 大尺度地图生成（城市布局）一次性
  omt        2 × 2                     ← 地图视图里的一格
    submap   12 × 12  (SEEXxSEEY)      ★ 加载/保存的最小单位
      map square (ms)                 ← 屏幕上的一个 tile
      reality bubble: 11 × 11 submaps  ← 以玩家为中心的活动区域
segment (seg)                          ← 仅用于 submap 的存盘格式
```

坐标类型系统用**编译期维度+原点+尺度的编码**（`point_abs_ms`、`point_sm`、`tripoint_rel`、`point_bub` 等），非法坐标在编译期就被拒绝。

### 8.2 分层流送的机制

实测文档描述的三层结构：
- **submap**：包含实际地图数据，`SEEX×SEEY` 块。车辆与 spawn 点用 vector 存（稀疏）。
- **mapbuffer**：全局 `MAPBUFFER` 单例，**把所有"曾经创建过"的 submap 常驻内存**（一个 cache，不是分层 cache）。
- **map**（`g->m`）：`MAPSIZE × MAPSIZE` 的 **submap 指针数组**（二维数组映射为一维数组），另有光照、气味等缓存。

**核心机制 —— 移动坐标系（shifting coordinate system）**：
> 当玩家移动到新的 submap，`map::shift()` 被调用，它**移动 `grid` 里的指针**以保持玩家居中。

```cpp
// DEVELOPER_FAQ.md 实测原文
void map::shift( point_rel const &dest )
```
玩家跨格时，只做「指针数组的 memcpy/搬移」（11×11 = 121 个指针，微秒级），**底层 submap 数据一个字节都不动**。

**这是一个惊人的设计取舍**：
- ✅ 零拷贝移动，玩家坐标永远在小范围内（局部 ms 坐标 ∈ [0,132)），整数运算不溢出
- ✅ 实体坐标不需要每次转换 —— CDDA 明确注释「coordinates of all entities on the map are shifted to accommodate this」，即**移动时批量改所有实体坐标**
- ❌ **所有实体坐标都是"相对的"**，存档时必须转为绝对坐标
- ❌ 任何需要真实世界坐标的系统（跨 submap 的弹道、跨格 AOI）必须做坐标变换

**与 UE World Partition 的对比**：
| | CDDA shift() | UE5 World Partition |
|---|---|---|
| 活动区域 | 固定 11×11 submap 数组 | 2D Runtime Hash 网格，cell 按需 |
| 坐标 | **移动坐标系**（数据不动，指针动） | 固定世界坐标，cell 按距离流送 |
| 加载粒度 | submap (12×12 tile) | cell (典型 256m×256m×256m) |
| 层次 | 四级 LOD（om/omt/sm/ms） | 三级（Grid Cell / Actor / HLOD） |
| 卸载 | 从 map 移除，但**留在 mapbuffer** | 按 Loading Range 卸载并释放 |
| 适用 | 回合制、格子移动、地形密集 2D-3D | 实时 3D 开放世界 |

**CDDA 的 `mapbuffer` 永不释放是刻意的**：程序化生成的地牢布局每次都不同，卸载后再加载必须重新生成（昂贵且不一致）。所以它选择「内存换一致性」。UE5 走的是相反路线（内存紧张，必须卸载）。**两种选择都正确，取决于内容的可重生成性。**

### 8.3 对现代引擎的启示

CDDA 的"级联 LOD 坐标系"（180 → 180 → 12 → 1）本质上就是**空间划分的层次化**：大尺度决定"这里是什么"，小尺度决定"这里具体长什么样"。UE5 的 `Runtime Spatial Hash`（editor hash 51200cm → runtime hash 3200cm）与此同构。

## B.1 空间数据结构族谱

| 结构 | 划分依据 | 深度 | 构建 | 剔除查询 | 最优场景 | 最差场景 |
|---|---|---|---|---|---|---|
| **均匀网格** Uniform Grid | 空间轴对齐 | O(1) | O(n) | O(1) 定位 + 链式遍历 | Doom blockmap、密集等尺寸对象 | 尺寸差异大 / 极端稀疏（开阔地形） |
| **BVH** | 几何中点/中面 | O(log n) 均 | O(n log n) | O(log n) | ioq3 `cNode_t`、追踪、光追 | 剔除依赖包围盒紧致度；需重建 |
| **BSP** | 分割平面 | O(log n) 不保证 | O(n log n) | O(log n) 且**天然得出可见性** | Quake 静态室内关卡 | **无法表达"门缝"外的空间**；凹形关卡退化 |
| **四叉树** QuadTree | XY 均分 | O(log n) | O(n log n) | O(log n) | 地形 LOD（OpenMW）、CDDA、UE WP grid | 非地形场景收益低 |
| **八叉树** Octree | XYZ 均分 | O(log n) | O(n log n) | O(log n) | 体素/SDF 加速结构 | 内存 8 倍系数浪费 |

| **DAG** 有向无环图 | 多父简化 | — | 离线 | 每节点独立 LOD 选择 | **Nanite** | 不能沿单一路径下降，需图遍历 |
| **Cluster graph** Cluster/图结构 | 语义簇 + 邻接图 | — | 离线 | 邻接遍历 + 剔除 | **Lumen** Surface Cache / 辐照度传播 | 簇边界处的光照渗漏 |
| **BVH over texture pages** | 纹理页 | O(log n) | O(n) | O(log n) | Virtual Texturing、Lumen SDF clipmap | 页管理开销 |

### B.1.1 各结构的本质差异

**BVH vs BSP —— 为什么 Quake 放弃了 BSP 作为渲染剔除结构**

BSP 的独特之处：分割平面同时定义了「节点划分」和「可见性区域划分」。Quake 的 PVS 之所以能预计算，正是因为 BSP 树把空间划分成**凸体（convex volume）的有向无环图**，凸体间的可见性是「全有或全无」的（要么完全可见要么被平面挡住）。

**但 BSP 无法表达开口**。一扇门在 BSP 里就是一个洞，可见性必须穿过洞继续传播 → PVS 编译需要处理 portal 拓扑 + 递归传播 + 合并，结果是 `DecomposeVis` 这类复杂逻辑和「过度保守」的可见集。

**BVH 不承诺可见性**。它只说「这个节点的内容在不在包围盒里」。可见性要在 GPU 上靠深度测试/HZB 现算。**这是 BVH 能处理任意几何（含开口、含 T 型接缝）而 BSP 不能的根本原因。**

> 实践建议：**物理碰撞用 BSP/AABB-tree（需要精确剖分、穿透测试），渲染剔除用 BVH（需要处理任意拓扑），两者共享同一份空间划分时用 BSP 生成的 leaf 作为 BVH 的叶子。** ioq3 的 `cLeaf_t` 同时带 brush 区间和 surface 区间，正是这种共享。

**DAG vs Tree —— Nanite 为什么必须是 DAG**

Tree 要求每个节点唯一父节点 → 简化某个 cluster 时，它的边界三角形必须与父节点严格匹配 → **产生裂缝（cracks）**。传统 LOD 通过「边缘裙边（skirt）」或「锁定边界边」规避，但这限制了简化的自由度。

DAG 允许多个父节点。实测 Nanite 的做法：
> Clusters gathered into groups of 8~32；每个 group 简化到约一半三角形后**重新切成 4~16 个新 cluster**；**decimation 保留 group 的共享边界不变，且分组在每层重新洗牌**，使得每条边最终都会在某一层被简化。

产生的是 DAG 而非树：`O(log N)` 的 cluster 选择变成图遍历（DAG 仍无环，所以遍历有界）。

**128 三角形的 cluster 大小**是权衡：太小 → GPU wave 内分支发散、per-cluster 开销占比过高；太大 → LOD 选择粒度粗、可见性剔除不精确。这是**现代版 Doom `checkcoord` 表**——把复杂决策预编译到细粒度单元里。

**Cluster graph（Lumen）—— 用语义簇代替几何簇**

Lumen 的 Mesh Card 不是几何划分，而是**每个物体与坐标轴对齐的六面各拍一次快照**。Surface Cache 是多张 4096×4096 纹理图集，存 Albedo/Normal/Depth/Emissive 等通道。

更新是**预算驱动的桶排序优先级队列**：
- 每帧最多更新 1024×1024 纹素的直接光照 + 512×1024 纹素的间接光照
- 128 个"桶"按优先级排序，优先更新**对视觉贡献大**的 Mesh Card
- 纹理空间满时**丢弃间接光照贡献低的 Mesh Card**（LRU 思想）

**这与 Doom 的 `Z_FreeTags(PU_PURGELEVEL)` 是同一个思想**：给每个资源打"重要度"标签，在内存/带宽预算下淘汰低价值的。

### B.1.2 GPU 端需要什么（任务书强调点）

**关键结论：GPU 剔除需要 CPU 侧的 BVH 是"紧凑、可预测、GPU 友好"的形态。**

CPU BVH 的常见形态不适合 GPU：指针跳转（无法 coalesce）、节点大小不等、无法随机访问。而 GPU 需要：
- **固定大小节点**（如 32/64 字节对齐），让 warp 内 lane 访问同一节点的连续字段
- **索引替代指针**（`child_left/child_right` 为 uint32 offset），让整个 BVH 能放在一个 buffer
- **保守 mip 选择**（见 B.3.2）

Nanite 的做法：把 cluster DAG 完全展平成 GPU 可读的大 buffer，compute shader 里遍历，无指针追逐。

> 实战建议：**CPU BVH 与 GPU BVH 分开构建**。CPU 版用二叉/四叉 + 指针（访问模式友好）；GPU 版用固定大小扁平节点数组 + 32 位索引（带宽友好）。同一份源三角形数据，两者各自构建。

## B.2 流送系统设计要点

### B.2.1 从 Doom 到 UE5：模型的三次演进

**代 1（Doom, 1993）：level 级批量切换**
- 机制：`PU_LEVEL` tag + `Z_FreeTags(PU_LEVEL)` 一次清空
- 粒度：整个关卡
- 策略：无（要么全在要么全不在）
- **问题**：切换瞬间内存尖峰（要同时持有旧关卡和新关卡）或长时间空窗

**代 2（Quake, 1996）：hunk 高水位 + LRU cache**
- 机制：`Hunk_LowMark()`/`Hunk_FreeToLowMark()` + `Cache_Move()` LRU
- 粒度：单个资源（模型、纹理、声音）
- 策略：LRU 驱逐
- **进步**：资源级生命周期，但仍是"整体关卡"边界

**代 3（UE5, 2022）：格子 + 优先级 + 形状化流送源**

实测 Epic 文档的关键参数与语义：

**格子（Runtime Grid）**
- `Cell Size`：典型 256m×256m×256m（大世界 12800-25600 cm）
- `Loading Range`：典型 25600 cm = 256m（社区实测默认值）；工程建议下限 12000 cm
- **网格提升（Grid Promotion）**：**比一个格子大、或有跨格硬引用的对象会被提升到更粗的网格层**。提升对作者不可见，但会静默膨胀加载集。

**流送源（Streaming Source）**
- 默认只有玩家相机；任意 actor 可通过 `UWorldPartitionStreamingSourceComponent` 成为流送源
- **多个流送源是并集**：任一流送源在范围内的格子都会加载
- **优先级**：多源相交时取**最高优先级**；**目标状态**取最高数值（Activated > Loaded）
- **形状**：默认为球，也可自定义
- 蓝图接口：`Enable/DisableStreamingSource`、`IsStreamingCompleted`

**必须成为流送源的四类 actor**（实测社区实践总结）：
1. **过场动画相机** —— 镜头飞过未加载区域会穿帮
2. **快速旅行预加载器** —— 传送前 2-3 秒激活目的地
3. **AI streamer** —— 无此则远处 AI 的 actor 引用悬空
4. **多人队友** —— 合作游戏中每个玩家在各自客户端隐式成为流送源；**服务器上所有玩家都需要成为流送源**（碰撞与玩法逻辑需要）

**这一清单是流送系统设计中最容易漏掉的**。绝大多数"流送 bug"最终都追溯到「某个 actor 需要数据，但它既不在已加载格里，也不在任何流送源范围内」。

### B.2.2 CDDA 的替代方案：坐标平移 + 全局 cache

见第 8.2 节。**适用判据**：
- 内容**不可确定性重生成**（程序化地牢每次不同）→ 必须常驻（mapbuffer）
- 内容**可确定重生成**（同一 seed 必然同一结果）→ 可卸载，必要时重生成

### B.2.3 参考计数资产生命周期

**id 的方案（hunk mark/release）**是"作用域式"：先进后出（LIFO），天然适合栈式生命周期（进关卡 → 出关卡）。
**UE5 的方案（cell 加载/卸载）**是"集合式"：非 LIFO，需要引用计数 + 依赖追踪。

UE5 的关键机制是 **`One File Per Actor`（OFPA）+ 硬/软引用分离**：
- **硬引用**（`TObjectPtr`）：actor 必须在场，否则引用悬空 → 会强制跨格加载 → 触发 grid promotion
- **软引用**（`TSoftObjectPtr` / `TSoftClassPtr`）：可延迟加载 → 允许流送

> **设计要点**：流送系统的核心难点不是"怎么加载/卸载"，而是**"怎么让引擎知道谁依赖谁"**。DOOM 时代是"关卡边界"（隐式全有全无），现代引擎必须显式建模依赖关系。

## B.3  剔除算法对比

| 算法 | 需要预计算 | 时机 | 精度 | 主要失效场景 | 开销来源 |
|---|---|---|---|---|---|
| **视锥剔除** Frustum | 无 | 每帧 | 精确（几何） | 无（总能算对） | 6 平面 × N 包围盒 |
| **Portal/PVS** | **离线 vis（编译期）** | 视线变化时 | 保守（可能过度） | 动态几何、portal 开关 | bitset 查表 + 节点标记 |
| **BSP 可见性** | 离线 vis | 同 Portal | 保守 | 同 Portal | 同 Portal |
| **HZB 遮挡剔除** | 无（当帧深度） | 每帧（用上帧深度） | **保守（不会漏）** | 需要正确的深度 | 深度金字塔构建 + 采样 |
| **双 pass HZB** | 无 | 每帧两次 | 保守 + 更少假阴性 | 仍会漏「新揭示」的物体 | 两轮 cull + 两次 HZB |
| **GPU-driven culling** | 无 | 每帧（GPU） | 同上 | CPU 完全不参与 | compute + indirect draw |

### B.3.1 视锥剔除的平面提取

实测 ioq3 `R_SetupFrustum` 的注释很关键：
```
Set up the culling frustum planes for the current view using the results
we got from computing the first two rows of the projection matrix.
```
**视锥平面直接从投影矩阵的前两行提取**（Gribb-Hartmann 方法），无需额外计算。这个技巧至今通用。

实测 ioq3 的优化：
```c
numPlanes = (tr.viewParms.flags & VPF_FARPLANEFRUSTUM) ? 5 : 4;
```
**默认只测 4 个侧面平面，不测远平面** —— 因为「超出远平面」在正常游戏里几乎不可能（且被 `zFar` 裁剪自然处理），省一次平面测试。**这是一个纯粹的性价比优化**，现代引擎同样默认 4 侧。

**对称视锥特化**（实测）：
```c
if(stereoSep == 0 && xmin == -xmax) {   // symmetric case can be simplified
    length = sqrt(xmax*xmax + zProj*zProj);
    oppleg = xmax / length;   adjleg = zProj / length;
    VectorScale(dest->or.axis[0], oppleg, dest->frustum[0].normal);
    VectorMA (dest->frustum[0].normal, adjleg, dest->or.axis[1], ...);
    ...
}
```
常规情况走预计算分支（每平面 2 次乘加），立体/非对称才走通用分支。**分支预测友好**。

### B.3.2 Hi-Z 层级深度与两阶段遮挡剔除

**Hi-Z 的构建**（实测算法描述）：
- Hi-Z 是深度缓冲的 mipmap 金字塔
- 标准深度缓冲：每个下采样 texel 存 **4 个子 texel 的最大深度**
- **Reversed-Z 深度缓冲**：存**最小深度**
- 这个"保守"性质保证 **mip level k 的单个 texel 代表该 2^k×2^k 屏幕 tile 上最远的可能表面**

**保守性的语义**：
> if an object's near depth is greater than the Hi-Z value, the object is definitely occluded
> 允许**假阴性**（本该剔除的没剔除 → 多画，不视觉错误），**禁止假阳性**（错误地剔除可见物体 → 穿帮）

**这是与 PVS 完全相同的非对称代价设计**（见 2.3.2）。所有可见性系统都必须遵守：**宁可多画，绝不错剔**。

**O(1) 测试**（实测伪代码）：
```hlsl
// 1. 8 个 AABB 角点变换到 Clip Space
// 2. 投影为 2D 屏幕包围矩形 (minX,minY)-(maxX,maxY)
// 3. 保守选 mip：让 AABB 恰好覆盖 4 个相邻 texel
mip = ceil(log2(max(rectWidth, rectHeight)))
// 4. 采样 4 个 footprint texel
max(box.z) > min(hiz.z)  →  Culled
// 5. 可见实例用 atomicAdd 追加到 indirect draw buffer
```
非正方形深度缓冲时 mip 选择需分别考虑宽高。

**双 pass 架构**（Nanite 同源，实测）：
```
Pass 1 (early draw)：用【上一帧】Hi-Z 测试
                      → 上一帧可见的对象立即绘制
                      → 用本 pass 的深度构建新的 Hi-Z
Pass 2 (late draw) ：用【本帧新】Hi-Z 重测上一帧被遮挡的对象
                      → 新揭示出来的对象在小批次里绘制
```

**为什么必须两 pass**：单 pass 用上帧深度会漏掉"上帧被挡、本帧该露出来"的东西（相机移动/物体移开）→ 视觉卡顿。用本帧深度则无延迟但需要等待所有几何绘制完 → 无法在同一帧早绘制。两 pass 是**延迟（1 帧）vs 视觉正确性**的折中，且 pass 2 只处理上一帧被遮挡的小集合，成本低。

实测社区数据：GPU-driven 剔除可消除 **70%–90%** 的被光栅化几何，且主线程 CPU 开销为零。

### B.3.3 Frustum + LOD 的组合策略

**它们解决的是不同层次的问题，不是竞争关系**：

| | 视锥剔除 | LOD |
|---|---|---|
| 问题 | "这个物体**在视野内**吗？" | "这个物体**该有多精细**？" |
| 判据 | 6 平面 + 包围盒 | 屏幕空间误差 / 距离 / 视角速度 |
| 层次 | object 级别 | triangle / cluster / tile 级别 |
| 交互 | **先剔后 LOD**：被剔的不参与 LOD 计算 | — |

**Nanite 的执行顺序**（实测）：
```
1. Cluster 选择：沿 DAG 下降，每层问"这个 cluster 的屏幕尺寸够吗"
2. Backface culling
3. Frustum culling（cluster 包围盒 vs 视锥）
4. Occlusion culling（双 pass HZB）
5. 三角形级 culling
6. 大三角形（>32px）→ 硬件光栅器
   小三角形（像素级）→ compute shader 软件光栅器（实测快约 3 倍）
7. 写入 64-bit visibility buffer：30 bits depth + 27 bits cluster + 7 bits triangle
   用 64-bit atomic 保证最近面获胜
8. 延后着色：读 visibility buffer，重建属性，只对可见像素求值材质
```

**第 7-8 步是关键的架构突破**：`visibility buffer` 把「几何处理」和「材质求值」彻底解耦。着色成本**只与可见像素数相关，与三角形复杂度无关**——一个 2000 万三角的模型若只占 5000 像素，着色开销与一个 2000 三角的模型占 5000 像素相同。

**这正是 B.2 中"重要性与优先级"思想的几何版本**：把有限的着色资源精确分配给贡献像素的几何。

### B.3.4 组合策略的推荐配置

| 场景 | 推荐组合 |
|---|---|
| 静态室内关卡（Doom/Quake 类） | BSP/PVS 离线 vis + 视锥；LOD 用 HLOD 远景替代 |
| 开放世界（UE5 类） | World Partition 格流送 + 视锥 + 双 pass HZB + HLOD；**portal 无用**（无预计算 vis） |
| 大量动态几何（GPU 粒子/植被风） | 纯 GPU-driven（Hi-Z + indirect draw），CPU 完全不参与 |
| 精确几何碰撞 | BSP/AABB-tree（需要穿透测试、精确接触面），**不要用 BVH 之外的近似** |
| 光线追踪加速 | BVH over triangles / SVO + 4 层 Clipmap（Lumen） |
| 地形 | 四叉树/Clipmap LOD + 格子流送（两套并存，见 7.1.2） |

# C. 对现代引擎的启示：历史包袱 vs 现代解法

## C.1 值得继承的（30 年证明有效）

| 经典做法 | 位置 | 现代继承 |
|---|---|---|
| **PVS/visframecount 打戳** | Quake `r_main.c` | 所有引擎的可见性标记都用单调计数而非清零 |
| **非对称代价：保守剔除** | Quake 8-unit FatPVS、Hi-Z max/min | 所有可见性系统的铁律 |
| **内存按生命周期分池 + 批量释放** | Doom `PU_LEVEL`/`Z_FreeTags`、Quake `Hunk_FreeToLowMark` | Arena/Allocator、`vkResetDescriptorPool` |
| **clipmodel 与 renderer 共享空间划分** | ioq3 `SetWorldVisData` | PhysX/几何缓存与渲染 BVH 共享 |
| **移动逻辑纯函数化** | Quake `pmove.c` | 所有确定性网络同步游戏的标配 |
| **数据与代码分离** | Doom WAD lump | 数据驱动配置（JSON/YAML/资产） |
| **剔除决策预编译查表** | Doom `checkcoord[12][4]` | GPU-driven culling 的分类表 |
| **可选优化 vs 必需正确性分离** | ioq3 `vised=qfalse` 回退全可见 | 任何"预计算加速"都应有 fallback |
| **高水位标记（LIFO mark/release）** | Quake hunk | Arena/栈式分配器、帧分配器 |

## C.2 必须抛弃的历史包袱

| 包袱 | 问题 | 现代解法 |
|---|---|---|
| **PVS 需要 BSP 编译期烘焙** | BSP 无法表达开口；动态几何无法纳入；改一堵墙要重跑 vis | 运行时 Hi-Z；或"CSG 编辑 → 编译"流水线（Cube/ET 保留但仅用于静态几何） |
| **`MAX_MAP_LEAFS` / `MAX_EDICTS` 静态上限** | 硬编译期常量；写死在头文件 | 动态容器 + 分块加载 |
| **单一世界模型（一个 `.bsp`）** | 关卡是原子单位，改一点要重导整个文件 | 格子化 + actor 级独立文件（OFPA） |
| **`float` 全精度几何** | 1996 年合理；现代带宽浪费 | half/量化（BVH 压缩、Nanite 14.4 bytes/triangle） |
| **单线程渲染** | 渲染与逻辑抢 CPU | 多线程渲染（ioq3 已有 worker：`cm` 的 trace 可并行）、render graph |
| **8/16/32 位定点** | 无 FPU 时代的必要 | float/half，但主机/移动端保留 SIMD 定点 |
| **逐个 `free()` 的 zone** | 无法批量回收，忘记 free 就泄漏 | 作用域 arena；`[[nodiscard]]`/RAII |
| **C 全局变量 + 头文件声明** | 隐式依赖；无法并行；编译期耦合 | 模块化（ioq3 `qcommon`）+ 显式上下文传递 |
| **世界坐标系固定 + 关卡切换** | 切换尖峰 | 格子流送（UE5）或坐标平移（CDDA） |

## C.3 现代引擎"看起来简单"背后的隐藏复杂度

1. **流送的依赖图必须显式建模**。DOOM 时代"关卡边界"隐式定义了所有依赖；现代引擎必须区分硬/软引用，否则一个跨格硬引用会导致 grid promotion、加载集静默膨胀。

2. **流送源不只是玩家**。过场相机、快旅预载、AI、队友——这四类是实践中最容易漏的。**这是系统性问题，不是单点 bug。**

3. **保守性有层级**。PVS 保守（少剔多画）、Hi-Z 保守（禁止假阳性）、Nanite 的 DAG 保守（边界不简化导致面数偏多）——每个"保守"都在用资源换正确性，要理解每个保守点的成本。

4. **LOD 策略必须可插拔**。OpenMW 的 `LodCallback` 是正确形态：四叉树结构稳定，细节判定策略可换（geomorphing / 屏幕误差 / 距离）。硬编码 LOD 距离的引擎在换美术风格时会全线返工。

5. **Nanite 的 visibility buffer 是架构级决策，不是优化**。它把几何处理与材质求值解耦，意味着整个渲染管线要重新组织（两趟、可编程光栅、64-bit atomic）。**这类"根本性简化"（continuous LOD 替代 discrete LOD）比渐进优化（更好的剔除）收益大得多。**

6. **空间划分应两层并存**（OpenMW 的 quadtree + cellstore，CDDA 的五级坐标）。流送层（数据在不在内存）与 LOD 层（用多精细）变更频率差一到两个数量级，强行统一必然两边都差。
