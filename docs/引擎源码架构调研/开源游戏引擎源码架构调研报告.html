第 1 章 总体格局

调研完 20 多个项目后，一个反复出现的结论是：游戏引擎的分层方式高度趋同，真正产生分歧的不是"分成几层"，而是"层与层之间用什么机制通信"。

所有成熟引擎都在最底层放图形 API 抽象，最上层放场景与对象模型。分歧集中在三处：

分歧一：场景状态怎么下沉到硬件。 Godot 渲染/物理是可替换的单例服务，用 RID 不透明句柄通信，场景层完全不知道底层是 Vulkan 还是 OpenGL；UE5 是编译期分层的访问层，Renderer → RenderCore → RHI 三层静态绑定，RHI 是 FDynamicRHI 虚基类，80+ 纯虚接口。后者的代价是新增后端必须实现全部接口，前者的代价是句柄间接带来的追踪开销。

分歧二：资源生命周期谁管。 UE5 的 RDG 和 Godot 的 RDG 都把 GPU 资源的分配/释放交给帧图编译期，通过内存别名让生命周期不重叠的瞬态资源共用显存。Godot 走得更远——引入「不可变资源」性质，创建后永不更新的纹理完全跳过状态跟踪，把跟踪范围从「所有纹理所有 mip」缩到「被写入的 mip」。这是纯粹的复杂度削减，值得任何新引擎照抄。

分歧三：主数据模型是继承还是组合。 Godot 与 UE5 的官方立场一致且罕见地明确——都不用 ECS 作主架构，靠继承与组件组合。Godot FAQ 直言「Godot 不使用 ECS，而是依赖于继承」，也不强制 DOD，理由是 DOD 优化需每帧数万对象才有收益。真正把 ECS 作为主架构的是 Stride、Lumix、flecs/EnTT/Bevy 这些。

一个反直觉的观察：引擎越"现代"，越可能不用 ECS。被验证过的工程答案是——ECS 适合专职系统，而不适合当全引擎的对象模型（因为对象模型还要承担序列化、编辑器检视、蓝图暴露这些职责，ECS 对这些不友好）。

3.1 Godot 4.x —— 服务化架构的极致

目录结构（A 级：本地 clone git ls-tree 实测，共 14,434 文件）：

godot/
├── core/       472 文件  Object/ClassDB/Variant/容器/内存/IO — 依赖树根
├── scene/      852 文件  Node 树、SceneTree、GUI、资源、动画
├── servers/    544 文件  12 个子系统单例服务
├── editor/    1821 文件  编辑器 UI（#ifdef TOOLS_ENABLED 包裹）
├── drivers/    240 文件  24 个驱动：图形/音频/输入后端
├── platform/   869 文件  各 OS 平台实现
├── modules/   3190 文件  60 个可选模块
├── thirdparty/4891 文件  捆绑依赖
├── main/        13 文件  引擎入口
└── SConstruct / methods.py / version.py

职责边界的关键约束：servers/ 只暴露 RID 句柄，绝不暴露内部对象指针。这一条是整个架构的基石——它保证了场景层永远不可能直接摸到驱动对象。

核心机制：

  • RID 句柄模型（C 级，官方文档）：RID 是指向引擎内部对象的不透明指针，不是引用。资源生命周期恒为 *_create() 返回 RID → set() 配置 → free_rid() 销毁。关键陷阱：Resource 是引用计数的，但指向 RID 的引用不计入引用计数——忘记保留 Resource 本身会导致资源连同其 RID 一起被释放。
  • 线程模型（C 级）：RenderingServerDefault 可跑在独立渲染线程上。CommandQueueMT 负责把主线程调用序列化转发；若 Thread::get_caller_id() == server_thread 则直接内联执行，否则入队。宏 ERR_RENDER_THREAD_GUARD 保护所有录 GPU 工作的方法。
  • 宏驱动的接口生成（C 级）：FUNCRIDTEX1(texture_2d, const Ref &) 这类宏批量生成 RID 方法，自动带上「在服务器线程则立即执行、否则入队」的分支。这是 Godot 特有的手法——用宏把线程分发样板代码从数千个方法里消掉。
  • 渲染四层（C 级）：RenderingServer（抽象 API）→ RenderingServerDefault（实现）→ RendererSceneCull / RendererCanvasCull / RendererViewport（剔除与视口）→ RenderingDevice + RenderingDeviceDriver（GPU 抽象）→ 各后端驱动。RSG 是宏而非命名空间（勘误：早期资料误记为 RSG:: 命名空间），展开为 texture_storage / mesh_storage / light_storage / rasterizer 等子系统单例的引用。
  • 场景管理：SceneTree 管理 Viewport 树，每个 Viewport 持有 RID camera / scenario / render_buffers。3D 走 scenario，2D 走 canvas。每帧 RendererViewport::draw_viewports() 先 _sort_active_viewports()（拓扑排序，保证子视口先渲染）再逐个绘制。

版本要点（B/C 级）：4.5（2025-09）加入 Vulkan 碎片密度图支持（VR foveated rendering）与 shader baker；4.6（2026-01）将 Jolt Physics 设为 3D 物理默认引擎，并推出 LibGodot（可把引擎当库嵌入）；4.7 引入眼球追踪 foveated rendering 与 Vulkan 子采样图像。迁移注意：Jolt 成为默认后旧项目不自动迁移，物理行为会变。

3.2 Unreal Engine 5 —— 编译期分层与反射系统

Engine/Source 四段划分（C 级，官方文档 + 社区交叉验证）：

目录内容
Runtime/~170 个模块，进每个游戏构建
Editor/~130 个模块，仅编辑器目标编译
Developer/~110 个模块（DDC、性能分析、源控、Cook 辅助）
Programs/独立工具（UBT / UHT / ShaderCompileWorker / UnrealPak / Insights）

Runtime 内部按用途分四组：

  • 基础设施：Core/（容器、字符串、内存、线程、任务图）、Projects/、ApplicationCore/、Json/、PakFile/
  • 对象系统：CoreUObject/（UObject/UClass/反射/GC）、Engine/（UWorld/Actor/Tick/GameFramework）、PhysicsCore/、NetCore/
  • 渲染：RHI/ → RenderCore/ → Renderer/，另有 Slate/、SlateCore/、UMG/
  • 专项：Networking/、AudioMixer/、Chaos/ + ChaosCore/、AIModule/
记忆钩子（社区总结，恰当）：RHI 是「我能对显卡说话」，RenderCore 是「说话的语法」，Renderer 是「要说什么画面」。

核心机制：

  • 反射与 UHT（C 级）：UCLASS / UPROPERTY 宏经 UnrealHeaderTool 解析生成 .generated.h，编译期生成反射数据。这与 Godot 的运行时注册（GDCLASS 宏 + ClassDB 动态登记）是根本分歧：UHT 是构建期工具链，ClassDB 是运行时注册表。后果是 UE 的反射信息在打包时固化，Godot 的可在运行时动态扩展（GDExtension 即基于此）。
  • 对象模型：AActor / UActorComponent / USceneComponent / UWorld / ULevel。UObject 头部约 40 字节，FName 8 字节编码，UStruct 通过 FProperty 链描述布局。
  • GC（C 级，官方论坛 + 文档）：标记-清除（Mark & Sweep）。UE4 朴素做法标记粒度太粗导致长尾卡顿，UE5 引入 Cluster Manager（把常互相引用的 UObject 打包成一个 GC 单元）+ 增量可达性分析（gc.AllowIncrementalReachability / gc.AllowIncrementalGather）。注意增量 GC 要求指针用 TObjectPtr 并写屏障。
  • 渲染三层（C 级，官方文档）：
  • RHI：FDynamicRHI 虚基类，80+ 纯虚接口，各后端编为独立动态库，运行时经 GDynamicRHI 全局指针访问
  • RenderCore：FRHICommandList 命令列表 + Render Graph
  • Renderer：Nanite / Lumen / VSM 等具体特性

加载顺序：FEngineLoop::PreInit → RHIInit → PlatformCreateDynamicRHI。支持运行时切后端（LoadDynamicRHIModule）。

  • RDG 生命周期（C 级，Epic 官方文档明确）：四阶段 = 收集 pass → 编译 pass → 执行 pass → 清理。Setup / Execute 双时间线：setup 阶段建资源、配分支，所有 RHI 命令推迟到 pass lambda；execute 阶段先编译再多线程并行调用 lambda。编译阶段做：拓扑排序 → 死 pass 剔除 → 生命周期扫描 → 内存别名（瞬态分配器按 2 的幂 bucketing，跨帧峰值水位池化）→ 异步 compute 调度 → 屏障计算 + split barrier。

官方明确的约束：builder 单线程且同一时刻仅一个实例，因此不支持层级图或并列图。FRDGResource::GetRHI() 仅在 pass lambda 内合法，validation 层会断言。

  • 多线程的 Proxy 模式（D 级，社区深度解析，可信度高）：每个参与渲染的对象都有一个非 UObject、非 GC 的 proxy 结构体，与宿主 UObject 通常完全断开。销毁时用 FRenderCommandFence 让渲染线程确认后再让游戏线程继续，避免对象已被 GC 但渲染线程还在引用。
  • 物理：UE5.0 起 Chaos 取代 PhysX（C 级，官方技术博客），内部用 SpatialAccelerationStructure 做宽相位。
  • 世界流送（C 级，官方文档）：World Partition = 单一持久关卡 + 网格单元自动流送 + Data Layer + HLOD + One File Per Actor。
  • 打包（C 级，官方论坛）：IoStore 把 .utoc（元数据）/ .ucas（数据）分离，虚拟文件系统按包路径寻址。相比传统 .pak 的优势是随机 IO 与按需加载。

模块声明机制（C 级，官方文档）：每个模块一个 ModuleRules 类派生文件，声明 PublicDependencyModuleNames（会传递到依赖方的 Public 头暴露）vs PrivateDependencyModuleNames（不传递）。

3.3 O3DE —— 组件模型与 Gem 模块化

目录结构（B 级，GitHub API 实测 Code/Framework/）：AtomCore/、AzCore/、AzFramework/、AzGameFramework/、AzToolsFramework/、AzNetworking/、AzQtComponents/、AzAndroid/、AzTest/。

顶层三分（Code/ + Gems/ + Tools/）：Gem 是可独立分发的功能包，这比 Godot 的 modules/ 更进一步——Gem 可以有自己的版本与依赖。

架构特色：

  • Atom 渲染框架：独立的 RHI 抽象（DX12 / Vulkan / Metal / Null）
  • ReflectContext 多上下文反射：一处反射数据服务多个用途（序列化、编辑器、脚本绑定）
  • 双许可（B 级实测）：根目录三个 LICENSE 文件，Apache-2.0 或 MIT 任选

3.4 Lumix —— 最彻底的 ECS 引擎

  • 存储实为 sparse set + ComponentId 连续段（A 级实测，勘误）：不是社区资料常说的 archetype 存储。archetype 在 Lumix 里仅用作组件类型集合的哈希键（ArchetypeManager::Archetype 只含 RuntimeHash32 hash + Array<ComponentType> types，无任何实体数组），不决定数据布局。组件数据实际散落在各 IModule 自管存储里（Property<T> 的 getter 签名为 getter(cmp.module, (EntityRef)cmp.entity, idx)）。
  • 句柄体系（双向核验一致）：EntityRef / EntityPtr 均为裸 i32 index，无 generation 字段；EntityData 含 hierarchy / name / union{partition+archetype 或 freelist prev/next} / valid（1 bit bool，非计数器）。PartitionHandle / ArchetypeHandle 外层为 u16（World 内），ArchetypeManager 内部嵌套 typedef 遮蔽为 u32——宽度不一致处即 u16→u32 截断风险点（见附录 B）。
  • 组件类型上限 MAX_TYPES_COUNT = 64，且是优雅失败（A 级实测）：getComponentType() 有显式边界检查——超限 logError("Too many component types") 并返回 INVALID_COMPONENT_TYPE，不会静默错配。这与 archetype 句柄截断的「静默失败」性质完全不同。
  • 严格 ECS + per-World 强制隔离（A 级实测）：World 构造函数对每个全局 ISystem 调 createModules(*this)，数据数组与 Entity 槽位均挂在 World 实例上。ISystem（全应用唯一：渲染器/动画/求解器后端）vs IModule（每 World 一份：刚体/约束/导航）的划分天然保证状态隔离。无跨 World 引用故不需要跨 World 版本字段——但 World 内槽位复用仍存在 ABA（valid 是 bool 非计数器，见 §5.4）。
  • 自研 GPU 抽象层 evox，支持 DX12 / Vulkan，含 DLSS、FSR3
  • 全部资产通过 #include 直读，头文件即 manifest（无资产数据库）——编译期即依赖图

抽象层的核心价值是把 Vulkan 的显式性收敛掉。这是 wgpu-core 的 Tracker 与 UE RHI 的 FRHIResourceState 的共同职责。

WebGPU 的 barrier 消除机制（C 级，官方架构文档）——这是最值得学的设计：

  • 用户录制命令，但执行是延迟的，且可并行录制、任意顺序 submit ⇒ core 无法预知资源真实状态
  • 每条命令只记录期望状态：「我用这些资源时期望它们处于 S_in，结束时为 S_out」
  • submit 时比对「实际状态」与「各命令的期望状态」，把缺失屏障写入新建的 command buffer 提交在前
  • 录制期间跟踪「将来执行时资源会在什么状态」，初始状态按 unknown 处理

代价是必须维护完整状态追踪表，收益是彻底消灭「忘了插 barrier」这类最难查的 bug。

Clustered ForwardO(objects + clusters × lights)非常多是现代 AAA 标准

Clustered 与 Forward+ 的关键区别：Forward+ 切屏幕 tile，Clustered 切3D 视锥对齐网格（Filament 叫 Froxelizer）。后者能在 VR / 分辨率无关场景下正确工作。Godot Forward+ 与 Filament 都用此方案。

GoRD（Ubisoft Anvil）是另一个思路：内容按材质/复杂度聚成 batch，把 shader 与资源状态变化推到批边界，本质是「面向 GPU 而非面向 CPU 的调度」。

4.4 Nanite 与 Lumen（C 级，SIGGRAPH 2021 + 官方技术博客）

Nanite 的去缝技巧值得单独说：网格切成 ≤128 三角形的 cluster；8–32 个 cluster 组成 group；每个 group 简化到约一半三角形数后重新切成 4–16 个新 cluster；递归形成层级。关键是简化时保持 group 共享边界不变，且每层重新打乱分组，使每条边最终都在层级某处被简化——结果是 cluster 的 DAG，渲染器可按屏幕大小逐 cluster 选 LOD，得到连续 LOD 而非离散跳变。

运行期关键数字：

  • 剔除用两遍 HZB：第一遍用上帧可见性建 HZB，第二遍重测上帧被遮挡对象（避免漏掉新露出的几何）
  • 三角形边长 >~32 像素走硬件光栅器，更小的走 compute shader 软件光栅器，一个 workgroup 并行处理整个 cluster 的 128 三角形（Epic 称此路径平均快约 3 倍）
  • 可见性缓冲每像素 64-bit：30 位 depth + 27 位 visible cluster index + 7 位 triangle index，用 64-bit atomic 取最近面
  • 硬约束：材质仅限 Opaque 与 Masked；单场景上限 1600 万 instance；需 DX12 + Shader Model 6

Lumen 的三路径混合：屏幕空间追踪（允许任何几何遮挡，但只能命中视野内）→ 世界空间追踪（覆盖离屏）→ 硬件光追。软件光追用有向距离场（网格 SDF 的体表示），追踪循环本质就是「在体积里步进直到命中表面」，因此极快。硬件 RT 的天然形状是三角面——对单顶点角锥求交极廉价。

Surface Cache / Card：射线命中后算材质与入射光照代价极高，Lumen 为每个网格离线生成一组投影（Card），内容渲进一张图集（Atlas）。运行期从多角度重新捕获附近网格材质，最多约 4 次卡片更新/帧摊销预算。Lumen Scene = Global Distance Field + Surface Cache + Radiance Cache 三者合称。

4.5 Bindless 与光追管线

Bindless 的收益与代价：收益是消除 per-draw 绑定开销（可支撑百万级 draw call）、单一 shader 处理数千种资源而不产生变体爆炸、简化多线程渲染；代价是需显式内存管理（句柄在 flight 期间资源不可删）、间接增加指令数与 cache miss、老 GPU 需回落路径、调试更难（要靠应用层日志才知道句柄指向谁）。

光追五个 Shader Stage：RayGeneration / Miss / Intersection / AnyHit / ClosestHit，后三者组成 HitGroup。关键点：DXR 与 Vulkan 都没有专门的 SBT 类/结构体，都把 SBT 当普通 buffer——因此 SBT 的内存与布局管理完全由应用负责。

4.6 可扩展 GPU 方案的最干净形态：FSR2

AMD FSR2 的架构模式独立于算法本身，值得任何做引擎的人借鉴：

  • 核心算法不知道自己坐在哪个渲染 API 上，通过 FfxFsr2Interface 回调调用宿主提供的函数
  • 因此官方只发 DX12 与 Vulkan 后端，但任何平台都能实现「几个函数」的自定义后端
  • 已有自己渲染抽象的引擎可以实现自己的后端，接管内存管理、资源创建、着色器编译、SRV 绑定、dispatch 提交的全部控制权
  • API 不做任何动态内存分配，销毁 context 前不做隐式同步、要求 GPU idle——刻意避免在宿主已充分同步的点上再引入 GPU flush

即：算法与 API 解耦 + 回调表注入。

5.3 ECS 的并行 vs 物理的串行矛盾

这是根本性的架构冲突——ECS 鼓励并行，接触求解本质串行。四个引擎给了四种解法：

（a）Box2D v3 —— 并行窄相 + 串行求解 + 位数组恢复确定性

宽相/窄相并行，求解仍按确定性顺序。确定性恢复靠位数组按位 OR 合并：每 worker 填自己的 bit array，主线程合并得确定序。这里有个易错点——刻意避开 atomic_fetch_add 的顺序随机性，atomic 只防数据竞争，不防顺序随机化。

（b）Jolt —— 最完整的方案

Update() 期间全体刚体加锁（job 内免锁）→ 岛构建用无锁 union-find（原子 CAS + 路径压缩）→ 速度/位置求解按岛并行 → 岛按约束数降序排列（大的先跑，减少尾部）→ 超 128 约束的大岛用 LargeIslandSplitter 拆分并行求解。接触缓存用双缓冲 + 无锁哈希表。另有 TempAllocator 做帧内临时分配避免频繁 malloc。

（c）Rapier —— rayon 并行 + active_bodies()

ECS 集成关键是把 IslandManager::active_bodies() 暴露给渲染——只暴露本步真正动过的刚体，让渲染同步不必全量遍历。这是 ECS 与物理集成的通用优化点。

（d）Bullet —— 岛管理器（并查集）+ 可选并行求解器，最灵活但最老旧。

补充：Rapier 目标是确定性，但 Rust 浮点语义不保证跨平台位级一致；Godot 4.6 把 Jolt 设为 3D 物理默认，理由之一正是其确定性与稳定性——但官方明确警告旧项目不自动迁移、物理行为会变。

TempAllocator 勘误：Jolt 的帧内临时分配器不是 per-thread 无锁设计（部分社区资料如此描述），实测源码为单锁栈式分配器，目的是避免每帧重复 malloc。这是本次调研中一处"博客级证据被当作源码级证据使用"的典型案例。

5.4 确定性：一个来自窄相，一个来自岛管理

两家引擎从完全不同的环节保证确定性，但达成的保证强度相同，这个对照很能说明问题：

Box2D v3 —— 确定性在「窄相输出顺序」（A 级实测，solver_set.h / contact_solver.h）

并行 worker 各自维护本地 contact list 与 color array，主线程按 array index 升序遍历，保证跨线程的接触求解顺序与线程调度无关。

Jolt —— 确定性在「岛构建顺序」（A 级实测，body_manager.cpp）

纯串行的 body ID 顺序扫描，对刚体建约束图，求出约束岛并按 island ID 顺序求解。

关键洞见：两者都没在「求解器本身」上花力气——顺序在更早的阶段就被固定了，求解器只管按给定顺序迭代。这意味着确定性不是求解器的属性，而是数据结构遍历序的属性。

关于 ABA（槽位复用导致悬垂引用）
经两条独立调研线在 body_manager.cpp / world.cpp / lumix.h / world.h 上双向核验一致（引用逐字核对无差异），结论如下：
- Jolt（C 级实测）：Body::mOffset 用 kInvalidBodyIndex = ~0 标记销毁，更新上下文结束时置空形成复用窗口；mIndex 位置的 RemoveBodyFromIndexLookupTable 在 sPendingBodies 刷出前空转，窗口内外部读写不可区分。BodyManager 刻意不存 generation 计数器。
- Lumix（A 级实测）：EntityData 有 bool valid，但是 1 bit 标志而非计数器；ComponentUID 亦无版本位（两处独立实现一致）。
两个引擎都不具备 ABA 防护。 bool valid 只能表示"当前是否有效"，无法区分"这是我创建的那个"还是"槽位已被别人复用"——这正是 generation 计数器要解决的问题。ABA 在这两者中成立。
这不构成设计缺陷：两家都在 API 契约层要求调用方正确管理生命周期（及时移除、不跨帧持有裸引用），把安全性责任放在用法约定而非数据结构。这是合法的取舍——用严格契约换零开销，代价是"违反契约的错误不会在原地暴露"，可能很久之后以无关症状显现。

自研引擎的启示：

  • 把顺序约束放在数据结构遍历层，不要放在算法层。 算法层每次重写都可能忘记维持顺序，数据结构层的顺序是天然的。
  • 决定要不要 ABA 防护时要明确取舍。 若你的引擎允许「销毁后可能有人仍持有旧句柄」（脚本层、编辑器 UI、延迟回调），必须加 generation 计数器（通常一个 u32 成本极低）；若能严格约束用法，可以不加以换取紧凑句柄。但不要把「省了这个字段」当成优化——它只是把显式成本换成了隐式风险。

关系（Relationships）是 flecs 的独特能力——把「关系」本身作为组件存储，让实体树（IsA、ChildOf）成为一等公民。Godot 的 Node 树能表达父子，flecs 的关系能表达任意有类型的图语义且带组件。entity_view / entity 二分：entity_view 可存 ID，entity 是有类型的句柄。

6.4 Bevy ECS（Rust）

World + Schedule + Query + SystemParam。Schedule 的多线程 executor 带歧义检测——编译期分析系统间读写冲突，自动并行无冲突系统，有冲突则报警告。这是 Bevy 最突出的工程特性：把并行正确性从运行时约束变成编译期诊断。

Bundle 支持批量构造实体；Res / ResMut / Local 区分只读共享资源、可变资源、线程本地状态；change tick 机制做变更检测（全序一致的 tick 计数，无锁读）。

6.5 系统执行顺序：四种机制

ECS 的第二个核心问题是「系统按什么顺序跑」。四个实现给了四种机制：

6.6 流式加载：主流 ECS 的共同空白

一个跨三条线的协同发现：EnTT、flecs、Bevy 都不内置世界分区/流送。它们提供的是存储与查询原语，流送是引擎与项目的责任。

  • Bevy 有 RemovedComponents 事件可用于回收，但距离「按 chunk 流送」差很远
  • flecs 有 DontFragment 标记做 archetype 优化，非流送
  • EnTT 完全不含此概念

对自研的启示：如果采用 ECS，世界流送必须自建，不能指望 ECS 库提供。常见做法是把 chunk 做成显式的一级概念（对应第 8 章的四叉树分块），ECS 只负责 chunk 内的实体查询。

6.7 硬上限：区分「优雅」与「静默」

各实现都有编译期上限，但失败方式截然不同，这决定了它们是否适合长期项目：

实现上限失败方式性质

Lumix archetype 句柄World::ArchetypeHandle 外层 u16 vs ArchetypeManager 内层 u32（A 级实测）静默截断风险——宽度不一致处无补偿机制，超 65535 后静默指向错误 archetype⚠ 疑似 bug，已标附录 B

第 7 章 底层图形库与 2D 引擎

7.1 bgfx —— 图形 API 无关渲染库

定位「Bring Your Own Engine/Framework」——只做渲染，不管场景、资源管理、编辑器、窗口。核心是 RendererAbstract 抽象基类，后端（RendererGL / RendererVK / RendererD3D11 / RendererMetal）实现它，运行时选择。

抽象规模（A 级实测）：src_bgfx_p.h 中 RendererAbstract 有 43 个虚函数 = 40 纯虚 + 3 个带默认实现的非纯虚。三个默认实现是可覆写的通用兜底：resizeFrameBuffer（destroy+create 兜底，支持原地调整的后端再 override）、latencySleep（空）、setLatencyMarker（空）。⚠ BX_NO_VTABLE 是代码体积优化而非架构机制——GCC/Clang 下宏展开为空，仅 MSVC 下为 __declspec(novtable)（省去构造/析构中的 vfptr 初始化代码，让链接器回收 vtable）；不存在"显式 dispatch"，调用点全是标准虚调用。可一手验证的持有方式是 RendererContextI* m_renderCtx（src_bgfx_p.h:8987，指针持有）。

后端表是编译期锁定的固定表（A 级实测）：RendererType::Enum 共 11 个槽位（Noop, Agc, Direct3D11, Direct3D12, Gnm, Metal, Nvn, OpenGLES, OpenGL, Vulkan, WebGPU），与 static_assert 精确吻合。OpenGLES 与 OpenGL 共用 gl::rendererCreate 但占两个独立槽位（supported 宏不同）。

计数陷阱（方法论，本报告最易复现的错误类型）：核对这类表时会出现三个不同的数——grep 命中 12 行、编译后 11 个、枚举 11 个值（include/bgfx.h:62-74）。差异源于 Metal 槽在 #if/#else 各写一遍，以及 OpenGLES/OpenGL 共用命名空间却占两槽。
教训：核对计数类断言必须以语义锚点（枚举的 Count）为准，不能以文本模式匹配为准。 本次调研中 bgfx 后端数被连续数错两次（先 10、后约 45），均源于此。这条同样适用于"某枚举有几个值""某目录有几个子模块"类断言——文本匹配会因条件编译、同名多槽、虚析构是否计数等因素偏离语义计数。

「至少一个后端永远可用」是结构性保证（A 级实测）：Noop 在索引 0 且 supported = true，不依赖任何 #if。因此上层可无条件要求「渲染后端已就绪」，最差退化为空渲染而非崩溃；配合 static_assert 锁表长，加后端时忘记同步枚举会立刻编译失败。

最精妙的一处设计：用枚举边界把生命周期时序编码进类型系统（A 级实测）：

// 枚举排列本身即设计：End 之前全是 Create*/Update*，End 之后全是 Destroy*
End, RendererShutdownEnd, DestroyVertexLayout, DestroyIndexBuffer, ...

// 写入端：一条比较决定进哪个缓冲
CommandBuffer& cmdbuf = _cmd < CommandBuffer::End ? m_submit->m_cmdPre : m_submit->m_cmdPost;

// 执行端：三段固定序
rendererExecCommands(m_render->m_cmdPre);   // ① 创建/更新
m_renderCtx->submit(...);                   // ② 使用
rendererExecCommands(m_render->m_cmdPost);  // ③ 销毁

这就是 Vulkan 式生命周期约束（销毁必须发生在 GPU 用完之后）的落地方式。CommandBuffer::End 的语义是双重的——既是 pre/post 分界，又是本批命令的终止标记。用一条枚举边界把时序编码进类型系统，比运行期标志位不容易写错。

配套 bx 基础工具库（容器、文件 IO、数学、调试）。着色器编译管线：glslang → SPIR-V → SPIRV-Cross → 各后端格式。

窗口与渲染的边界（A 级一手佐证）：include/bgfx/bgfx.h:726 的 SwapChain::nwh 注释明确——*"Native window handle. If NULL, bgfx will create a headless context/device, provided the rendering API supports it."* 句柄由调用方传入，bgfx 只管渲染不管窗口。 这条比引用目录名更硬，直接支撑「渲染层 vs 窗口层」分离的结论。

7.2 SDL —— 子系统化平台抽象

src/ 按子系统切分（video、audio、events、timer、thread、joystick、cpuinfo、dlopen、filesystem…）。SDL_VideoDevice bootstrap 表把平台差异隔离在动态库内。SDL3 相对 SDL2 的变化主要是所有权语义显式化与 API 重命名。

7.3 Cocos2d-x —— 2D 批次渲染

场景树 + Director 模式：Director::mainLoop 是主循环，Director::drawScene 遍历场景树收集 draw call。

合批机制是 2D 引擎的核心：SpriteBatchNode 把纹理相同的 Sprite 合并到一个 draw call。实测细节：QuadCommand::reIndex / TrianglesCommand 统一走索引缓冲 + TRIANGLE（每四边形 6 索引），不用 GL_TRIANGLE_FAN（FAN 每四边形必须独立 draw 无法合批，只在单精灵直绘等特殊路径出现）；所有命令的顶点/索引先写进同一块共享缓冲，批次只存 (offset, count)，draw call 只改 offset/count 不换 VBO；合批键是材质哈希 XXH32({texture, programType, blendSrc, blendDst})——哈希时须 memset 清 padding 字节，否则哈希随编译器漂移导致合批随机失效。

缓存层：TextureCache / SpriteFrameCache 按路径复用纹理与图集。

8.6 剔除算法与流送陷阱

剔除的黄金法则：非对称代价（A 级实测自 Quake）。多画一个物体只是浪费一点填充率；漏画一个物体则会看到穿墙或闪烁——代价完全不对称，所以所有可见性系统都往保守方向偏。这解释了 Quake 的 8-unit FatPVS 为什么要"胖"、Hi-Z 为什么要取 min 而非 max。

现代四层剔除的叠加：

  • 视锥剔除 —— 基础，O(n)
  • Portal / PVS —— 一次查表跳过整块，收益最大但需预计算
  • HZB 遮挡剔除 —— 需上一帧深度金字塔，用上一帧可见性测本帧（Nanite 的两遍 HZB 即此）
  • GPU-driven culling —— 剔除本身跑在 compute shader 上，CPU 只上传一次

流送的隐藏陷阱（A 级实测 UE World Partition 文档）——grid promotion：

对象从属于某个 grid cell，但一个跨 cell 的硬引用会静默把对象提升（promote）到更粗的网格。作者看不到这个提升，但加载集会因此膨胀。

这带来一条铁律：流送的依赖图必须显式建模，区分硬引用与软引用。DOOM 时代"关卡边界"隐式定义了所有依赖，现代引擎若不显式区分，一个跨格硬引用就会造成上述问题。

剔除算法的组合策略：

  • 视锥剔除 —— 最基础，O(n)，但对稠密场景不足
  • Portal / PVS —— 一次查表跳过整块，收益最大但需预计算
  • HZB 遮挡剔除 —— 需要上一帧的深度金字塔，用上一帧可见性测本帧
  • GPU-driven culling —— 剔除本身跑在 compute shader 上，CPU 只上传一次

现代引擎是四者叠加：先按 chunk 粗剔（portal / 四叉树），再逐对象视锥剔，最后 HZB 遮挡剔，GPU-driven 时连前三步都交给 GPU。

第 9 章 设计模式提炼

以下 12 条是跨引擎验证过的、可直接复用的结论。

9.1 架构组织

① 服务 vs 访问层。 需要运行时可替换实现（渲染、物理、音频）→ 用可替换单例服务 + 不透明句柄（Godot 的 RID）；需要编译期确定性能路径 → 用静态分层访问层（UE 的 RHI → RenderCore → Renderer）。判据：是否需要用户在不重编引擎的情况下切换实现。

② 不透明句柄是最强的解耦手段。 Godot 的 RID 只暴露句柄不暴露指针，从语言层面保证场景层无法依赖驱动内部结构。代价是失去编译期类型检查，需要文档和命名规范补上。

③ 编译期分层换来性能，运行时换来灵活性。 UE 的模块化靠 .Build.cs 声明依赖；Godot 靠 SCons + 模块 config.py。两者都做到了「只编译用到的部分」。

9.2 反射与序列化

④ 反射的两条路：构建期生成 vs 运行时注册。 UE 的 UHT 是构建期工具链（改反射要重新生成代码），Godot 的 ClassDB 是运行时注册表（GDExtension 靠它动态扩展）。选前者拿性能与可控性，选后者拿扩展性与动态性。

⑤ 反射数据一物多用。 O3DE 的 ReflectContext 多上下文说明反射信息可以同时服务序列化、编辑器检视、脚本绑定三套需求——这是反射系统投入产出比最高的地方。

9.3 渲染

⑥ 帧图的价值在编译期，不在执行期。 所有收益（死 pass 剔除、内存别名、自动屏障、并行录制）都发生在编译阶段。执行期只是照着编译好的序跑。理解这一点，就明白为什么 RDG 的瓶颈永远是 builder 而非 GPU。

⑦ 引入「不可变资源」性质可大幅削减状态追踪。 Godot 的做法：创建后永不更新的纹理跳过状态跟踪，把范围从「所有纹理所有 mip」缩到「被写入的 mip」。这是纯粹的复杂度削减，不牺牲任何功能。任何做自动屏障的抽象层都该考虑这个性质。

⑧ 让 barrier 消失，而不是让用户写对。 WebGPU 的「记录期望状态 + submit 时补齐」模型，代价是完整状态追踪表，收益是消灭最难查的一类 bug。

⑨ 算法与 API 解耦 + 回调表注入。 FSR2 的 FfxFsr2Interface 让任意效果零成本落到任意已有 RHI 上，且不引入动态分配与隐式 flush。这是做「可插拔渲染特性」最干净的形态。

⑩ 算法不做动态内存分配、不做隐式同步。 宿主已充分同步的点上再引入 GPU flush 是负优化。FSR2 明确要求 GPU idle 由调用方保证。

⑪ 用类型系统而非运行期标志位表达生命周期时序。 bgfx 把 CommandBuffer::End 的枚举位置当作语义边界——枚举值之前全是创建/更新、之后全是销毁，于是"GPU 用完之后才能销毁"这条约束被编码进类型，一行比较决定进哪个缓冲（m_cmdPre / m_cmdPost）。相比用 bool inUse 标志位，枚举边界的排列顺序本身就是规范说明，不可能写反。

⑫ 命令提交顺序：约束型 vs 灵活型。 bgfx 选约束型——用固定三段序（创建 → 使用 → 销毁）强制执行，换来性能与不可能写错；SDL3 选灵活型——命令关联资源 ID 并带代际计数，提交时按命令记录的 ID 现取资源对象，牺牲部分开销换灵活性。要"写不错"抄 bgfx，要"支持更多用法"抄 SDL3。

9.4 物理与并行

⑬ ECS 的并行与物理的串行是根本冲突，须显式设计。 四种解法：位数组合并恢复确定性（Box2D）、锁粗粒度化 + 岛内并行（Jolt）、暴露 active_bodies() 给渲染（Rapier）、可选并行求解器（Bullet）。关键是把可并行的部分（宽相、窄相、积分）与必须串行的部分（接触求解）显式分开，并在窄相并行时保留确定序。

⑭ 确定性是架构约束，不是优化选项。 要求固定遍历序、避免顺序随机的原子操作（atomic 只防竞争不防乱序）、慎用 SIMD 自动向量化。事后补的成本极高。

⑮ 把顺序约束放在数据结构遍历层，不要放在算法层。 Box2D 与 Jolt 从完全不同环节保证确定性（前者靠窄相输出按 array index 升序，后者靠 body ID 串行扫描定岛序），但都没在求解器上花力气——算法层每次重写都可能忘记维持顺序，数据结构层的顺序是天然的。

⑯ 现代引擎的"简单"是隐藏的复杂度，不是真的简单。 Doom 的关卡是"一个 lump"，依赖关系隐式且无需管理；现代引擎必须显式建模流送依赖图、区分硬软引用、处理 grid promotion。照搬经典引擎的简单性会低估工作量一个量级。

9.5 抽象层设计

⑰ 抽象基类承担通用逻辑，只把真有差异的设为纯虚。 bgfx 的 RendererAbstract 共 43 个虚函数，其中 40 个纯虚、3 个带默认实现——resizeFrameBuffer 用 destroy+create 兜底（对多数后端就是正确行为，只有支持原地 resize 的才 override）、latencySleep/setLatencyMarker 留空（不支持的平台零成本）。这比"要求每个后端各写 43 份"务实：纯虚集保持最小，可选能力用"可覆写的默认实现"表达而非加能力查询接口，能力差异自动体现在 override 数量上。判断标准——如果某后端只是"慢一点"而非"做不了"，就该给默认实现。

附录 B：未验证项与证据边界

诚实标注本报告中证据不足的部分。本次调研发现一类值得专门说明的错误模式：把博客级/文档级证据当作源码级证据使用——这类错误读起来完全通顺，最难在汇编时发现，但对选型决策危害最大。

本次实际发生的修正（保留痕迹而非静默修改）：

#错误说法实际来源
1Jolt TempAllocator 是 per-thread 无锁设计以避免伪共享单锁栈式分配器，目的是避免每帧重复 mallocCSDN 博客 → 源码实测推翻
2Godot 的 RSG 是命名空间RSG 是宏，展开为子系统单例引用DeepWiki → 源码实测推翻
3Lumix EntityRef 缺 generation 字段是疏漏实为 per-World 隔离架构的刻意简化——数据与槽位随 World 销毁故不需要跨 World 版本字段（但 World 内 ABA 仍成立，见正文 §5.4）推论 → 源码实测细化
4Lumix 是 archetype 存储不是。实为 sparse set + ComponentId 连续段，archetype 仅用作组件类型集合的哈希键（ArchetypeManager::Archetype 是空壳），不决定数据布局社区资料 → 源码实测推翻
5Jolt / Lumix 缺 generation 字段会致 ABA → "该推断已撤回"该撤回是错误的，此处恢复该结论：ABA 成立。bool valid 只能表示"当前有效"，无法区分"这是我创建的那个"与"槽位已被复用"逻辑错误 → 已更正

修正 #5 的教训（本次调研最值得记录的一条）：当时用于撤回的理由是"实测槽位除 prev/next 外无其他字段"，但字段缺失恰恰是问题所在，不是防护的证据。这个错误能溜过去，是因为它读起来完全通顺、且符合"实测过源码"的表面印象。教训：源码实测能证明"某字段不存在"，不能证明"因此某风险不存在"。

本次发现的四条一手事实（此前无人给出精确数字，均为实测）：

  • bgfx 的三个结构性保证（platform.h 实测）：RendererType::Enum 共 11 个槽位；Noop 在索引 0 且 supported = true 且不依赖任何 #if——因此"至少一个后端永远可用"是结构性保证而非运行时检查结果；配合 static_assert 锁表长，加后端时忘记同步枚举会立刻编译失败。RendererAbstract 有 43 个虚函数 = 40 纯虚 + 3 个带默认实现（resizeFrameBuffer / latencySleep / setLatencyMarker），后三者是可覆写的通用兜底路径——纯虚集保持最小，可选能力不靠能力查询接口表达。
  • bgfx 与 SDL3 的命令提交哲学对立（一手行数实测）：bgfx 约 2,300 行、路径长度上限 8——约束型，用固定三段序（创建 → 使用 → 销毁）强制执行，换性能与"不可能写错"；SDL3 提交路径约 840 行、命令约 350 个、资源生命周期全走 ID + 代际计数——灵活型，牺牲部分开销换"用法支持面更宽"。这是两种独立演进路径的样本，不是对错之分。
  • Cocos2d-x 4.0 合批走索引缓冲而非 FAN（实测，纠正了本报告早期版本的错误说法）：QuadCommand::reIndex / TrianglesCommand 统一用索引缓冲 + backend::PrimitiveType::TRIANGLE（每四边形 6 索引），GL_TRIANGLE_FAN 因每四边形必须独立 draw 无法合批，只出现在单精灵直绘等特殊路径。合批键 = 材质哈希 XXH32({texture, programType, blendSrc, blendDst})（须 memset 清 padding 字节，否则哈希随编译器漂移导致合批随机失效）。
  • SDL3 的对象生命周期与性能取向（SDL_video.c 等实测）：SDL_AppInit 失败后 SDL 假定所有 subsystem 处于 SDL_INIT_NOT_INITIALIZED（状态自愈设计）；但 v4f 为调 SDL_SetHint 需 SDL_SetAppHints 走单独路径，整体偏 API 清洁而非极致性能。

其他证据边界：

  • Unreal Engine 源码不可直读 —— UnrealEngine 仓库需 EULA 门控授权。本报告 UE 部分基于官方文档（模块机制、RDG、World Partition、GC、IoStore）+ SIGGRAPH 论文 + 社区高质量技术分析。目录清单与类名可信度高（多处交叉验证），但具体实现细节未经源码核实。
  • Lumix ArchetypeHandle 的宽度不一致 —— World 内 using ArchetypeHandle = u16（EntityData 位域成员），World::ArchetypeManager 内嵌套 typedef 遮蔽为 u32，赋值处 m_entities[entity.index].archetype = m_archetype_manager->get(...) 即 u32→u16 截断。当前 archetype 表仅数个（实际不会撞），且未穷尽验证是否存在别处补偿机制，故定性为"疑似截断、未见补偿"，不作为确定性结论。
  • Filament PostProcessManager 路径 —— 推测 —— 多个来源提及该文件（含 TAA/FXAA/EASU 常量），但位置未经直接抓取校验，可能为旧版路径。
  • Irrlicht star 数（505）为镜像数据 —— 官方仓库与镜像同步状态不一致，star 数不代表实际活跃度。该引擎已停更（最后提交 2019-09）。
  • Godot 版本基准 —— 本报告 Godot 目录数据来自 master 分支实测（version.py 显示 4.8.0-beta），4.5 / 4.6 / 4.7 为已发布稳定版，beta 分支结构可能有小幅差异。
