## 1. 图形抽象层对比表

| 维度 | Vulkan | DX12 | Metal | WebGPU（wgpu / Dawn 实现） |
|---|---|---|---|---|
| **资源模型** | `VkImage`/`VkBuffer` +显式 `VkImageLayout`；`VkDeviceMemory` 手动 suballocation | `ID3D12Resource` + `D3D12_RESOURCE_STATES` 显式枚举 | `MTLResource` 隐式 hazard tracking（可选手动） | `GPUTexture`/`GPUBuffer`，用户**不接触状态**；状态由实现推导 |
| **命令模型** | `VkCommandBuffer`（录制）→ `vkQueueSubmit`；`VkCommandPool` 分配 | `ID3D12GraphicsCommandList` → `ExecuteCommandLists` | `MTLCommandBuffer` + 独立 `MTLRenderCommandEncoder` | `GPUCommandEncoder` → `GPUCommandBuffer` → `queue.submit()` |
| **同步原语** | `vkCmdPipelineBarrier2`（`VkMemoryBarrier2` / `VkImageMemoryBarrier2`）+ `VkEvent` / `vkCmdSetEvent` + `vkCmdWaitEvents` + `VkSemaphore` | `ResourceBarrier`（state / alias / UAV 三类）+ `SplitBarrier`（begin/end）+ `Fence` | 驱动自动插 fence（encoder 之间）；`memoryBarrier` 可选 | 无用户可见 barrier；`queue.submit` 边界隐式同步；映射用 `mapAsync` |
| **描述符** | `VkDescriptorSetLayout` + `VkDescriptorPool`，set/binding 显式 | `ID3D12RootSignature` + 描述符堆 + table | `MTLArgumentEncoder` 内的 buffer/texture 表 | `GPUBindGroupLayout` + `GPUBindGroup`，由 pipeline layout 校验 |
| **扩展性** | vendor extension / layer；`VK_EXT_*` | `ID3D12Interface` 扩展接口 | Metal feature set 版本 | `GPUAdapter.features` / `limits`；`wgpu::Features`、`DownlevelFlags` 分级 |
| **多队列** | 原生多 family（graphics/compute/transfer）+ ownership transfer | 队列 + fence + 显式 ownership | 单一命令队列（推测：Metal 无用户可见多队列） | `GPUQueue` 单一队列 + 内部 fence |
| **分层范式** | 无官方抽象层，业界自建 RHI | 同左 | 同左 | `wgpu-hal`（unsafe，零校验）→ `wgpu-core`（安全，全校验）→ `wgpu`（idiomatic） |

**结论**：Vulkan/DX12 把"何时同步"完全上抛为应用责任，Metal/WebGPU 走隐式。抽象层的核心价值就是把 Vulkan 的显式性收敛掉——这正是 `wgpu-core` 的 `Tracker` 与 UE `RHI` 的 `FRHIResourceState` 的共同职责。

> **补充：这是「原生 API」维度的对比。引擎自建抽象层还有另一种形态**——bgfx 的「后端表 + noop 回落」（§2.4）走的是**运行期查表**而非 WebGPU 系的静态分发，且**不接管状态管理**（barrier 交给各后端自己处理）。它比 WebGPU 系更轻、比裸 Vulkan 更省事，是可插拔抽象的**第三种范式**。

## 2. wgpu / Dawn：WebGPU 的双实现

### 2.1 架构与目录

**wgpu（Rust，gfx-rs/wgpu）**是分层 crate 架构，自下而上：

- `wgpu-hal`：**完全 unsafe** 的可移植 API，静态分发（`vulkan::Api` / `metal::Api`），**零校验零跟踪**，转换开销最小。traits：`Api`、`Instance`、`Adapter`、`Device`、`Queue`、`Surface`、`CommandEncoder`。要求显式调用 `transition_buffers` / `transition_textures`，并要求持久映射（buffer 可长期 mmap，靠 `map_buffer` 声明同步点）。这是 `gfx-hal` 的精神继承者但范围收窄。
- `wgpu-core`：建在 hal 之上，**面向不可信输入**（"bullet-proof"）。负责参数校验、资源生命周期（用 `Arc` 满足 hal 的 outlive 要求）、跨设备使用检查、`MemoryInitTracker`（惰性零初始化，在 map 与 submit 时插入）。
- `wgpu`：面向用户的惯用 API，含 `backend::wgpu_core`（native/Emscripten）、`backend::webgpu`（wasm 直连浏览器，`Backend::BrowserWebGpu`）、`backend::custom`（动态分发用户自实现）。
- `naga` / `naga-types` / `wgpu-naga-bridge`：着色器翻译（WGSL/SPIR-V/GLSL → MSL/HLSL/GLSL/SPIR-V），并把 `wgpu::Features` / `DownlevelFlags` 映射为 naga `Capabilities`。
- `wgpu-types`（`no_std`）、`wgpu-sync`（跨平台锁原语）、`wgpu-core-remote` + `wgpu-core-remote-types`（跨进程序列化状态）。

**关键设计**：hal 的「纹理内部不同 mip/array 层可处于不同状态，Buffer 只有单一状态」这一非对称性，直接决定了 core 里barrier 生成的粒度。

**Dawn（C++，Chromium 内 WebGPU 实现）**：

- `dawn.json` 描述 native WebGPU 的数据模型 → `generator/dawn_json_generator.py`（Jinja2 模板）**代码生成** headers、C++ wrapper、proc table、wire 序列化/反序列化。
- `src/dawn/native/` = `dawn_native`：**frontend**（全部状态跟踪与校验）+ 子目录后端（`d3d12`、`metal`、`vulkan`、`opengles`）。内嵌 `spirv-val`，用 **Tint** 把 WGSL 转成 HLSL（D3D12）/ MSL（Metal）/ SPIR-V（Vulkan）。
- `src/dawn/wire/` = `dawn_wire`：client 把命令序列化成buffer，server 反序列化、校验、再调 `dawn_native`。**刻意做最少的 state tracking**，让 client 保持精简。（推测）这条设计使 Chromium sandbox 进程可以极薄。
- `src/dawn/platform/`：依赖注入接口定义（DI，取代第三方 C++ 库）。
- `dawn_proc`：静态 `dawnProcTable`，把 `wgpuDeviceCreateBuffer` 转发到 `procTable.deviceCreateBuffer`。用途：运行时决定走 native 还是 wire（同二进制测两条路径）、应用可一次性取全部 entrypoint 而非反复 `wgpuGetProcAddress`。

WebGPU 对象模型分层：`navigator.gpu`（`GPU`）→ `requestAdapter()` → `GPUAdapter` → `requestDevice()` → `GPUDevice` → `device.queue`（`GPUQueue`）。着色侧：`GPUShaderModule` + `GPUPipelineLayout` + `GPUBindGroupLayout` → `GPUBindGroup` → `GPURenderPipeline`/`GPUComputePipeline`（后者含 `GPUBindGroupLayout` 校验）。

### 2.2 核心类型/接口表

| 层 | 类型 | 职责 |
|---|---|---|
| wgpu-hal | `Api` / `Instance` / `Adapter` / `Device` / `Queue` / `Surface` / `CommandEncoder` | 后端抽象，全部 `unsafe`，静态分发 |
| wgpu-core | `Tracker` | 记录资源集合、当前状态、CB 期望初始状态；保持 sampler/pipeline 等无状态资源存活 |
| wgpu-core | `MemoryInitTracker` | 追踪 buffer 内存初始化状态，惰性插零 |
| Dawn | `dawnProcTable` / `dawnProc` | 入口点间接层，运行时切换 native/wire |
| Dawn | `dawn.json` / `dawn_wire.json` | 生成器的数据模型 |

### 2.3 机制剖析：barrier 如何被"消失"

这是抽象层最值得学的机制。流程：

1. 用户在 `CommandEncoder` 里录制，但**执行是延迟的**，且多线程可并行录制、任意顺序 submit ⇒ core **无法预知**资源真实状态。
2. 因此每个 `wgpu_core::CommandBuffer` 只**记录**「我用这些资源时，期望它们处于状态 S_in；我结束时它们处于 S_out」。
3. `Queue::submit` 时，core 逐一比对「资源实际状态」与「每个 CB 的期望状态」，把缺失的屏障写入一个**新建的 `wgpu_hal::CommandBuffer`**，提交在它前面。
4. 录制期间，`CommandEncoder` 跟踪「将来执行时资源会在什么状态」，据此在流内加屏障；每个资源的**初始状态按 unknown 处理**。

这等价于把 Vulkan 的 `VkImageLayout` 全部自动化。代价是必须维护完整的 state 追踪表（`Tracker`），收益是彻底消灭「忘了插 barrier」这类最难查的 bug。

### 2.4 对照：bgfx 的「后端可插拔」是第三种范式

前两节讲的是 WebGPU 系（wgpu / Dawn）。**bgfx 提供了一个更早、也更轻的对照物**——它解决的是同一个问题（多后端抽象），但用完全不同的手段。（以下路径均已对本地源码快照 `_gfx/bgfx/` 逐条核验。）

**抽象接口**：`src_bgfx_p.h:5949` 的 `RendererContextI` 是纯虚基类，**40 个纯虚方法 = 39 个纯虚成员函数 + 1 个虚析构**（`~RendererContextI() = 0`），覆盖 `createVertexBuffer` / `createShader` / `createProgram` / `createTexture` / `createFrameBuffer` / `submit` / `flip` / `isDeviceRemoved` 等。它标了 `BX_NO_VTABLE`，但**这个宏的实际语义常被误解**，见下方「`BX_NO_VTABLE` 的准确语义」。

**`BX_NO_VTABLE` 的准确语义**（已在 bx 库头文件与 MSVC 官方文档上双向核实）：

该宏定义在 **bx 库**（`include/bx/macros.h`）而非 bgfx 仓库，**按编译器分叉展开**：
```c
#if BX_COMPILER_GCC || BX_COMPILER_CLANG
#	define BX_NO_VTABLE                 // ← 展开为空
#elif BX_COMPILER_MSVC
#	define BX_NO_VTABLE __declspec(novtable)
```
**所以「这个基类不生成 vtable」只在 MSVC 上成立**——GCC/Clang 下它什么都不是。MSVC 官方文档（`learn.microsoft.com/en-us/cpp/cpp/novtable`）原文：

> "The `__declspec` stops the compiler from generating code to initialize the vfptr in the constructor(s) and destructor of the class. In many cases, this removes the only references to the vtable that are associated with the class and, thus, the linker will remove it. Using this form of `__declspec` can result in a **significant reduction in code size**."
> "This form of `__declspec` can be applied to any class declaration, but **should only be applied to pure interface classes**, that is, classes that will never be instantiated on their own."
> "If you attempt to instantiate a class marked with `novtable` and then access a class member, you will receive an access violation (AV)."

**准确结论**：
- 它停止生成的是**构造/析构中的 vfptr 初始化代码**，目的是让链接器回收 vtable，**属代码体积优化**；
- 它**不是**「禁止虚调用」，**也不是**「强制显式 dispatch」——调用点全是**标准虚调用**（`m_renderCtx->submit(...)`（`src_bgfx.cpp:3471`）、`m_renderCtx->flip()`（`:3389`）、`m_renderCtx->createIndexBuffer(...)`（`:3987`）），后端侧是标准 `override`（`src_renderer_gl.cpp` 41 处、`src_renderer_vk.cpp` 42 处、`src_renderer_d3d11.cpp` 43 处、`src_renderer_mtl.cpp` 40 处）；
- 它**要求该类为纯接口类**（绝不被单独实例化）——`RendererContextI` 恰是（40 个纯虚、不可实例化），**用法与文档要求完全匹配**。

> **可借鉴的是一条工程约束，而非架构范式**：「接口基类标 `__declspec(novtable)`，前提是它绝不会被实例化」。多后端时链接器可回收重复的 vfptr 初始化代码，代码体积收益可观。但**这不该被当成「抽象层怎么设计」的范式**——真正的设计启发是下面那三条（表恒长、noop 结构性保证、静态断言），不依赖这个宏。
>
> 另注：`struct Frame` 在 `src_bgfx_p.h:668` 只有**前向声明**、无定义，且 `m_renderCtx` 是**指针持有**（`src_bgfx_p.h:8987`）而非内嵌——因此「可塞进 POD 结构而免 RTTI 开销」一类说法无源码依据，本报告不下此结论。

**后端注册**：`src_bgfx.cpp:3650` 的 `s_rendererCreator[]` 表，每项是 `{createFn, destroyFn, name, supported}`（结构定义在 `src_bgfx.cpp:3640`）。后端只导出两个符号 `rendererCreate(const Init&)` / `rendererDestroy()`，由 `BGFX_RENDERER_CONTEXT(_namespace)` 宏（`src_bgfx.cpp:3620`）统一声明。**编译后 11 个槽位**，与 `RendererType::Count` 精确吻合（`include_bgfx_bgfx.h:62-74`）：

```
Noop, Agc, Direct3D11, Direct3D12, Gnm, Metal, Nvn, OpenGLES, OpenGL, Vulkan, WebGPU
```

> **计数陷阱（完整链条）**：源码文本 **12 行** → 编译后 **11** → 枚举 `Count` **= 11**。两个坑叠加——① Metal 槽在 `#if`/`#else` 里各写一遍（非 Apple 平台回落为 `{ noop::..., false }`）；② `OpenGLES` 与 `OpenGL` 是**两个独立槽位**但共用一个 `gl::` 命名空间。**唯一可靠的口径是 `RendererType::Count`**，任一单看都会数错。

**三个设计细节（比帧图更早解决「后端可插拔」）**：

1. **`supported` 字段由编译期宏定死**——`!!BGFX_CONFIG_RENDERER_D3D12` 之类，不是运行时探测。
2. **索引 0 恒为 noop 且 `supported = true`**（`src_bgfx.cpp:3652`）。这比「平台不适配时回落 noop」更重要——它使「**至少有一个后端永远可用**」成为**结构性保证**，不依赖任何 `#if`。主引擎因此可以无条件要求「渲染后端已就绪」，最差情况退化为空渲染（不崩、不黑屏），而不是崩溃。
3. **`static_assert(BX_COUNTOF(s_rendererCreator) == RendererType::Count)`**（`src_bgfx.cpp:3669`）锁死表长与枚举数一致——新增后端忘记加枚举会**立刻编译失败**，而不是运行时静默错位。

**运行时兜底还有第二层**：`src_bgfx.cpp:3397` 检测到 `m_renderCtx->isDeviceRemoved()` 时，销毁当前 context 并**回落到 noop 后端**（注释原文 "Something horribly went wrong, fallback to noop renderer."）。即「设备丢失」不是崩溃，而是降级到能继续跑的最小实现。

**与 WebGPU 系的对比**：

| 维度 | wgpu / Dawn | bgfx |
|---|---|---|
| 分发方式 | 静态分发（`vulkan::Api` 泛型）+ `Backend::Custom` 动态分发 | 运行期查表（`s_rendererCreator`） |
| 缺失后端 | 编译期不选 | **运行期回落 noop**，表长恒定 |
| 着色器 IR | `naga`（WGSL 中心）→ 各后端 | **glslang → SPIR-V → SPIRV-Cross** → DXBC/DXIL/MSL/GLSL；Vulkan 直吃 SPIR-V |
| 状态管理 | 自动 barrier（`Tracker`） | **后端各自处理**，抽象层不管 |

**着色器 IR 的显式版本档位**（`tools_shaderc_shaderc.cpp:147-151`）值得抄——SPIR-V profile 显式枚举且**版本号与 profile 号成对给出**：
```
{ ShadingLang::SpirV, 1010, "spirv10-10" }   // SPIR-V 1.0, profile 10
{ ShadingLang::SpirV, 1311, "spirv13-11" }   // SPIR-V 1.3, profile 11
{ ShadingLang::SpirV, 1411, "spirv14-11" }
{ ShadingLang::SpirV, 1512, "spirv15-12" }
{ ShadingLang::SpirV, 1613, "spirv16-13" }
```
这比「只写一个 `spirv` 」健壮得多：不同后端对 SPIR-V profile 的支持度不同，**把版本与 profile 绑成一对作为编译契约**，比让后端各自猜测要可靠。

**渲染层与窗口层的边界**：`include_bgfx_bgfx.h:726` 的 `SwapChain::nwh` 是**原生窗口句柄，由调用方传入**（注释："Native window handle. If `NULL`, bgfx will create a headless"）。即 bgfx **只管渲染，窗口由调用方给 native handle**——与 §2.4 开头「窗口/输入/GLFW 胶水全在 `examples/common/entry/`」的分工一致。做「渲染层 vs 窗口层」结论时注意别引用不存在的路径（据 arch-graphics 核实，当前版本 bgfx 已无 `platform/` 目录；本地快照为精选文件集，此项未能由我直接验证）。

**线程模型：单线程触碰 GPU 上下文**

`src_bgfx.cpp:2547`：`m_thread.init(renderThread, this, 0, "bgfx - renderer backend thread")`。主线程把绘制写进 `CommandBuffer`（`src_bgfx_p.h:1145`），渲染线程消费后调 `m_renderCtx->submit(...)`（`src_bgfx_p.h:6153` 的 `renderThread` 只是 `while (RenderFrame::Exiting != bgfx::renderFrame()) {}` 的循环壳，真正逻辑在 `Context::renderFrame`，`src_bgfx.cpp:3436`）。

**API 调用无锁 + GPU 上下文只在单一线程碰**——这是与 UE RDG「多线程并行录 pass」的**根本分歧**：UE 追求 pass 级并行，bgfx 追求**上下文单线程化**（Vulkan/D3D 的 context 大多非线程安全，这个约束比并行收益更实际）。

**命令缓冲的一个精妙细节**：`CommandBuffer::Enum`（`src_bgfx_p.h:1174`）在 `End` 处把命令分成两段——`End` 之前是 `RendererInit` / `Create*` / `Update*` / `Resize*`，`End` 之后是 `RendererShutdownEnd` / `Destroy*` / `ReadTexture` / `ReadBuffer`。`getCommandBuffer()` 据此选 `m_cmdPre` 或 `m_cmdPost`：

```cpp
// src_bgfx_p.h:6151
CommandBuffer& cmdbuf = _cmd < CommandBuffer::End ? m_submit->m_cmdPre : m_submit->m_cmdPost;
```

`Context::renderFrame`（`src_bgfx.cpp:3436`）的执行顺序是 **`cmdPre` → `submit()` → `cmdPost`**：

```cpp
// src_bgfx.cpp:3455-3494
BGFX_PROFILER_SCOPE("bgfx/Exec commands pre",  kColorResource);  rendererExecCommands(m_render->m_cmdPre);
BGFX_PROFILER_SCOPE("bgfx/Render submit",       kColorSubmit);   m_renderCtx->submit(m_render, m_clearQuad, m_mipGen, m_textVideoMemBlitter);
BGFX_PROFILER_SCOPE("bgfx/Exec commands post", kColorResource);  rendererExecCommands(m_render->m_cmdPost);
```

这个划分正是 **Vulkan 式的资源生命周期约束**：销毁必须发生在 GPU 用完之后，所以 destroy 类命令被推迟到 submit 之后的那一段。**用一条枚举的边界把「创建 / 使用 / 销毁」三段时序编码进类型系统**，比用运行期标志位更不容易写错。

> **`End` 的语义是双重的**（`src_bgfx.cpp:3914` 与 `:3970`）：它既是「pre/post 的分界」，**又是「本批命令的结束标记」**——
> ```
> case CommandBuffer::End:  return;      // :3914  pre 缓冲：遇到即结束
> case CommandBuffer::End:  end = true;  break;  // :3970  post 缓冲：置结束标志
> ```
> 同一枚举值承担两种角色：**分界标记**与**终止符**。这比用两个独立枚举更省事，也更难写错。

> **主引擎可借鉴的表述**：「定义命令枚举时，把会引用 GPU 资源的操作放中间，把释放资源的操作放显式边界之后。」

**对照案例：SDL3 的依赖检测式（不同构，勿混为一谈）**

SDL3 的 `FlushRenderCommands`（`SDL_render.c:308`）解决的是**同一个问题**（GPU 资源不能在途时释放），但机制**完全不同**：

| 维度 | bgfx | SDL3 |
|---|---|---|
| 队列结构 | **双段** `m_cmdPre` + `m_cmdPost`，由 `CommandBuffer::End` 枚举边界划分 | **单段** `render_commands` 一条链表 |
| 时序保障 | **结构性**：枚举边界 + 一次比较，销毁自动排到 submit 之后 | **依赖式**：靠 generation 计数检测队列是否引用该资源 |
| 关键代码 | `_cmd < CommandBuffer::End ? cmdPre : cmdPost` | `FlushRenderCommandsIfTextureNeeded` |
| 错误倾向 | 上层写错顺序也不会 UB | 漏更新 `last_command_generation` → use-after-free |

SDL3 的依赖检测（`SDL_render.c:344`，由 `SDL_DestroyTextureInternal` 在 `:5782` 调用）：
```c
static bool FlushRenderCommandsIfTextureNeeded(SDL_Texture *texture)
{
    if (texture->last_command_generation == renderer->render_command_generation) {
        // the current command queue depends on this texture, flush the queue now before it changes
        return FlushRenderCommands(renderer);
    }
    return true;
}
```

**结论**：**要「写不错」抄 bgfx（编码进类型），要「灵活」抄 SDL3（运行期按依赖检测）。** 两者不可写成「统一模型」——SDL3 的方案允许更动态的队列编排，代价是正确性依赖调用方维护 generation 计数。（对照数据由 arch-graphics 实测提供，见其笔记 `调研_底层图形库与2D引擎架构.md` SDL3 节 (d)。）

### 2.5 惰性合批：CPU 侧合并 vs GPU 侧打包

与帧图正交的另一个减负手段。**Cocos2d-x 4.0 的合批是纯 CPU 侧的**（`cocos_renderer_CCRenderer.cpp:552` 的 `Renderer::drawBatchedTriangles()`）：

- 所有命令的顶点/索引先写进**同一块大缓冲一次上传**；
- 批次只存 `(offset, indicesToDraw)`；
- draw call 只改 offset/count，**不换 VBO**；
- 批次切分依据是 **`materialID`**（`cmd->getMaterialID()` 相等则并入当前批），并用 `cmd->isSkipBatching()` 逐条豁免。

对照 Skia 的 `GrDrawOpAtlas`（GPU 侧打包）——**同一问题的两种解法**：Cocos 在 CPU 侧合并索引，Skia 在 GPU 侧打包 draw op。

> **对帧图设计的启示**：帧图解决的是「pass 与资源依赖」，**合批解决的是「同一 pass 内 draw call 数量」**——两者正交且可叠加。
>
> 更进一步：Cocos2d 的 `materialID` 定义是 `XXH32({texture, programType, blendSrc, blendDst})`（据 arch-graphics 实测）——**一个状态快照的哈希**。因此「**合批键 = 状态等价类**」在 Cocos2d 里是**字面成立**的，不是类比。这与 Nanite 的「按材质分 bin」（§5 步骤 [L3]）是同一形式，只是粒度不同。
>
> **批次边界的本质是「状态变化点」，因此合批算法与状态机是同一件事。**

## 3. 帧图 / 渲染调度

### 3.1 UE5 Render Graph (RDG)

RDG 是**立即模式 API**：把渲染命令录进图数据结构，随后编译执行。官方列出的能力：异步 compute fence 调度、最优生命周期与内存别名的瞬态资源分配、**split barrier** 做子资源转换以隐藏延迟、并行命令列表录制、无用资源与 pass 剔除、API 用法与依赖校验、RDG Insights 可视化。

**四阶段生命周期**：`收集 Pass → 编译 Pass → 执行 Pass → 清理`。

- **Setup 时间线**：建资源、配置管线分支；所有 RHI 命令推迟到 pass lambda。
- **Execute 时间线**：先编译，再多线程并行调用 lambda 向 RHI command list 录命令。执行单个 pass = 前序（`BeginRenderPass`）+ 主体（调lambda）+ 后续（`EndRenderPass`）。

**核心类型**：

| 类别 | 名称 | 说明 |
|---|---|---|
| Builder | `FRDGBuilder`、`FRDGBuilder::AddPass`、`AllocParameters`、`CreateTexture`/`CreateBuffer`、`CreateUAV`、`RegisterExternalTexture`、`Execute` | 单线程，同一时刻只能有一个实例 |
| Pass flags | `ERDGPassFlags::Raster` / `Compute` / `AsyncCompute` / `NeverCull` / `Copy` / `SkipRenderPass` | 决定队列与行为 |
| 资源 | `FRDGTextureRef`/`FRDGTexture`、`FRDGBufferRef`/`FRDGBuffer`、`FRDGUniformBuffer`、`FRDGTextureUAV` | `CreateTexture` 建的为瞬态（可别名），`RegisterExternalTexture` 导入的只跟踪 barrier 不别名 |
| 访问/状态 | `ERDGTextureAccessFlags`、`ERDGBufferAccessFlags` | 推导依赖边与生命周期 |
| 参数宏 | `BEGIN_SHADER_PARAMETER_STRUCT` / `SHADER_PARAMETER_RDG_TEXTURE` / `RENDER_TARGET_BINDING_SLOT` / `END_SHADER_PARAMETER_STRUCT` | 生成元数据→ RDG 抽取依赖边（读边←写边→） |
| 工具 | `FComputeShaderUtils::AddPass`、`FPixelShaderUtils::AddFullscreenPass`（`RenderGraphUtils.h`） | 减少样板 |

Shader 参数结构体经 `FShaderParametersMetadata`（含 `FMember`：名称、C++/HLSL 类型、字节偏移）反射，RDG 据此遍历 pass 参数。**`FRDGResource::GetRHI` 仅在pass lambda 内合法**，validation 层会断言。

编译阶段做的事（生产级五步 + 三扩展）：拓扑排序 → 从输出反向可达性剔除死 pass（UE 用引用计数，被剔除 pass 不分配资源、不发屏障）→ 生命周期扫描 → 内存别名（瞬态分配器 `r.RDG.TransientAllocator`，2 的幂次 bucketing，跨帧峰值水位池化；Frostbite 则是持久 heap + 自定义 bin size）→ 异步 compute 调度 → 屏障计算 + split begin/end → 屏障批处理。Frostbite 与 UE 的关键区别：UE 是**混合式重建**（缓存拓扑，变更或引擎事件时失效），Frostbite 是**每帧全量重建**。

### 3.2 Godot 4 RD RenderingDevice + RendererRD

Godot 的渲染器**完全构建在 OpenGL 与 RenderingDevice 之上**，后者是它对 Vulkan/DX12/Metal 的抽象。四种渲染方法：

- **Forward+**：前向 + **聚簇光照**，compute shader 把光分到 3D 视锥对齐网格，像素查自己所在 cell。桌面高效，移动端低效。
- **Forward Mobile**：传统单pass 光照，纯光栅 shader（无 compute），因移动端 tile-based 渲染而设计。
- **GL Compatibility**：唯一支持 OpenGL 驱动的方法，传统单 pass。
- Mobile 的两个关键改动：3D 不用 RGBA16F 而用 **R10G10B10A2 UNORM**（带宽减半，移动硬件对 32-bit 格式优化更好，代价是 HDR 能力受限）；尽量用 **sub-pass**（限制是不能读邻近像素，故 glow/DOF 无法高效实现）。

**类层次**（Godot 4.x）：

| 类 | 角色 | 位置 |
|---|---|---|
| `RenderingDevice` | 唯一底层 GPU 公开入口，单例；所有录 GPU 工作的方法受 `ERR_RENDER_THREAD_GUARD()` 保护 | `servers/rendering/rendering_device.h` |
| `RenderingDeviceCommons` | 共享枚举/类型/`DataFormat` | `rendering_device_commons.h` |
| `RenderingDeviceDriver` (RDD) | 硬件无关驱动接口，`DEFINE_ID` 包装原生句柄 | `rendering_device_driver.h` |
| `RenderingContextDriver` | 交换链、surface、设备枚举 | `rendering_context_driver.h` |
| `RenderingDeviceGraph` (RDG) | 命令录制、重排、屏障插入 | `rendering_device_graph.h` |
| `RenderingDeviceDriverVulkan` / `...D3D12` / `...Metal` | 具体实现 | `drivers/vulkan/` 等 |

资源全部用 `RID` 引用，由 `RenderingDevice` 通过 `RID_Owner` 成员管理；有依赖图保证释放父资源（如 `Shader`）时级联清理依赖者（如 `Pipeline`）。CPU→GPU 上传走 **staging buffer 池**（`StagingBuffers` / `StagingBufferBlock`，各有 Upload/Download 用法）。启动时用 `_get_device_type_score()` 打分选设备（独显 5 分、集显 4 分）。Vulkan 驱动可用 `re-spirv` 针对 specialization constant 优化着色器。

**Godot 的 RDG 设计取向**（Clay John, Vulkanised 2024）：灵感来自 Pavlo Muratov 的文章，目标是「尽可能 automagic」——用户**不手建图**，而是录制 "command"（更新/拷贝/清纹理或缓冲、提交 render list / compute list）；命令**总是从合法状态出发和结束**；RDG 从渲染代码**推断**命令，自己排 barrier 与资源转换。一个关键优化是引入**不可变资源**（创建后永不更新的纹理/缓冲），从而**只跟踪被写入的 mip**，大幅降低跟踪成本。官方日志清晰展示了层次：`Capture Start` → 命令图 L-1 → `Render Setup (L0, Copy)` → `Render Depth Pre-Pass (L1, Draw)` → `Render Opaque Pass (L2/L3)` → `Draw Sky (L4)` → `Render 3D Transparent Pass (L4/L5)` → `Tonemap (L6)` → `vkCmdBeginRenderPass(Clear)` / `vkCmdDrawIndexed` / `vkCmdEndRenderPass(Store)` → `vkQueuePresentKHR`。

注意 Godot 用 **specialization constant** 管理 shader permutation（对应上文 Vulkan 驱动的 `re-spirv`），这在 WebGPU 生态里没有对应物。

### 3.3 Filament

Google 的实时 PBR 引擎，主打 Android/iOS 体积与效率。

**仓库结构**：`filament/`（引擎本体，`backend/` 放 Vulkan/Metal/OpenGL-ES 驱动）、`libs/`（`filabridge`、`filamat`、`gltfio`、`bluegl`/`bluevk` 等绑定与工具）、`tools/`（`matc` 材质编译器、`cmgen` IBL 生成、`mipgen`、`resgen`）、`shaders/`、`third_party/`。

**分层**（自上而下）：App Code → **Engine**（资源生命周期与线程，公开 API）→ **Renderer**（帧编排，`beginFrame` / `render(view)` / `endFrame` 循环）→ **Scene**（ECS：`RenderableManager`、`LightManager`、`TransformManager`，SoA 布局）→ **View**（相机、合成、后处理参数）→ **Material / MaterialInstance** → **FrameGraph**（pass 调度）→ **Clustered Forward Renderer**（光聚簇 `Froxelizer`）→ Shadow（CSM/VSM/PCSS）→ Post-Processing（Bloom、DoF、TAA、tone mapping）→ 后端。

`CommandStream` 是线程安全环形缓冲区：Engine 线程录命令，Render 线程回放。渲染流程：`renderJob` 里以 `mResourceAllocator` 为入参构建 `FrameGraph` → 取 `Blackboard`（FrameGraph 全局资源管理器，存共享虚拟资源如阴影图、RenderTarget）→ 依可见性构建 `RenderPass` → **编译并执行**。`endFrame` 做 `SwapChain::commit`、`FrameInfoManager::endFrame`、`CommandStream::tick`、`mResourceAllocator.gc`。

**FrameGraph 源码结构**（`filament/src/fg/`）：`FrameGraph.h/.cpp`、`FrameGraphPass.h`、`FrameGraphRenderPass.h`、`FrameGraphId.h`、`Blackboard.h`、`DependencyGraph.h`、`details/PassNode.h`、`details/ResourceNode.h`。工具库 `libs/fgviewer` 提供 `DebugServer` + web 前端实时查看图结构。

**核心机制**：
- **虚拟资源**：声明阶段只有描述符（`FrameGraphTexture::Builder` 设 format/size/usage），`devirtualize` 后才占真实显存。
- **双 lambda**：每个 pass 是「立即执行的 setup lambda」+「延迟的 execute lambda」——与 UE RDG 的双时间线同构。
- **版本化**：每次 `builder.write()` 都新建一个 `ResourceNode` 代表该资源的新版本，从而在细粒度上正确推导读写序。
- **剔除**：`compile()` 移除引用计数为 0 且未被标为 target 的节点。
- `FrameGraph` 内部用 `LinearAllocatorArena` 做高性能内存分配。
- 排序：draw command 用 64-bit key 排序以最小化状态切换。

PBR 特性清单（官方）：Cook-Torrance 微表面高光 BRDF、Lambertian 漫反射、金属工作流、clear coat、各向异性、sheen/布料、半透明近似、IBL、物理相机与物理光照单位、点/聚/平行光阴影、级联阴影、EVSM/PCSS/DPCF/PCF、彩色半影、透明阴影、接触阴影、SSAO/SSR/SSR 折射、全局雾、**动态分辨率（支持 AMD FSR）**；后处理含 HDR bloom、DoF bokeh、多种 tone mapper（GT7 / PBR Neutral / AgX / ACES / filmic）、色彩管理（luminance scaling、gamut mapping）、调色（曝光/夜间适应/白平衡/通道混合/ASC CDL）、TAA/FXAA/MSAA。

> 注：任务书中提到的 `PostProcessManager` 路径 `filament/src/PostProcessManager.cpp` 在多源中出现（含 TAA/FXAA/EASU 常量），但该文件位置未经我直接 fetch 校验，**（推测）为旧版路径**。

## 4. 现代渲染技术机制

### 4.1 Nanite

**问题**：三角形缩到像素级时固定管线光栅器效率骤降，传统做法是美术手工做多级 LOD + 面数预算。

**导入期**：网格切成 **≤128 三角形**的 cluster；8–32 个 cluster 组成一个 group；每个 group 被**简化到约一半三角形数**，再**重新切成 4–16 个新 cluster**；递归该过程形成层级。**关键去缝技巧**：简化时保持 group 的共享边界不变，且**每层重新打乱分组**，使每条边最终都在层级上某处被简化——结果是 cluster 的**有向无环图（DAG）**，渲染器可按屏幕大小**逐 cluster 选 LOD**，得到**连续 LOD** 而非离散跳变。

**运行期**：
1. **剔除**：视锥 + **两遍 HZB**。第一遍画上帧可见对象并由其构建 HZB；第二遍用新 HZB 重测上帧被遮挡的对象，避免漏掉新露出的几何。
2. **LOD 选择**：按 cluster 屏幕投影尺寸在 DAG 中选节点。
3. **光栅**：**三角形边长 >~32 像素**走硬件光栅器；更小的走**compute shader 写的软件光栅器**，一个 workgroup 并行处理整个 cluster 的 128 个三角形。Epic 称此路径平均比硬件光栅器**快约 3 倍**。
4. **可见性缓冲**：两个光栅器写**同一个** visibility buffer，每像素一个 **64-bit 值，30 位 depth + 27 位 visible cluster index + 7 位 triangle index**，用 **64-bit atomic** 取最近面。
5. **延迟着色**：可见性缓冲完成后，独立 pass 读 cluster/triangle ID、重建表面属性，**只对可见像素**求值材质。这把着色成本与几何成本解耦。
6. **流式加载**：压缩格式，「Valley of the Ancients」样本平均 **14.4 字节/输入三角形**（百万面 ≈13.8MB，约比带 4 级 LOD 的标准静态网格小 **7.6 倍**），按 cluster 粒度按需驻留。Epic 建议用 SSD。
7. **调试**：内置可视化（Nanite Clusters viewmode 看 LOD 分布、光栅模式热力图）、GPU profiler 中的 VisBuffer / Material Classification / Emit GBuffer 等 pass。

**硬约束**：材质仅限 **Opaque 与 Masked**（半透明不走 Nanite 路径）；单场景上限 **1600 万 instance**；需 **DX12 + Shader Model 6**；旧前向渲染器、MSAA、完整光追在 Nanite 路径外/仅实验性。UE 5.5 起支持 Nanite 骨骼网格（实验性）。

### 4.2 Lumen

**目标**：全动态 GI + 反射，默认开启，面向次世代主机 60FPS 大型开放世界。

**三条追踪路径混合**：① **屏幕空间追踪**——先对屏幕追踪，允许任何几何类型遮挡间接光，但只能命中相机视野内物体；② **世界空间追踪**——先试屏幕追踪，不可靠时回退到世界空间以覆盖离屏物体；③ **硬件光追**。

**软件光追（默认）**用**有向距离场**（signed distance field）：网格 SDF 是 3D 曲面的**体表示**（volume buffer），原始三角网格的近似；UE4 时代编辑器就能离线为每个静态网格生成 mesh distance field，UE5 改进为支持大物体流式加载。SDF 追踪极快，因为整个追踪循环基本就是**在体积里步进直到命中表面**。多个网格会合并成 **Global Distance Field**以加速重叠场景（官方 demo「Lumen in the Land of Nanite」因重叠极多，全程只用 Global Distance Field）。硬件光追更准更贵，能表示更多几何类型（含蒙皮网格），**镜面反射必须用硬件光追**。RT 三角面数很少、单调、不可修改 → 对**单顶点角锥（cone）**求交极廉价，这也是硬件 RT 的天然形状。

**Surface Cache / Cards / Atlas**：射线命中后要算材质与入射光照，若每条光线末尾都求值材质会极贵且低效（多射线命中同一点、材质有大量纹理查找）。Lumen 为每个网格**离线生成一组投影**（想象成物体表面的**反转 cube map**），这些投影面/捕获位置称为 **Card**，用 `r.Lumen.Visualize.CardPlacement 1` 可视化；默认每个网格 12 个卡，可在静态网格编辑器的 **Max Lumen Mesh Cards** 增加。这些卡的内容被渲染进一个大的**图集（Atlas）**。运行期从多角度重新捕获附近网格的材质属性（**Lumen 反复重捕获卡片**），最多约 4 次卡片更新/帧摊销以控制预算；未被覆盖区域在 Surface Cache 视图模式下显示粉色，命中时反射为黑。相关 CVar：`r.LumenScene.SurfaceCache.AtlasSize`、`r.LumenScene.SurfaceCache.ResolutionScale`、`r.LumenScene.SurfaceCache.ResidesNumFrames`、`r.LumenScene.SurfaceCache.MeshCardsMinResolution`。

**Radiance Cache**：追踪一组 radiant probe 的间接光，结果供 Final Gather 查询；离线烘焙到 LumenCard 贴图里，运行期「重新光照」（relight）后写回多帧使用。

**Lumen Scene** = 三者合称：Global Distance Field（体）+ Surface Cache（图集）+ Radiance Cache。**Lumen Scene 就是光追器实际看到的几何**，可在视口 `Show → Visualize → Lumen Scene` 查看——这是排查光照问题第一个该看的工具。GI 与反射是**统一求解**的，复用部分追踪结果，因此反射里天然包含漫反射 GI 与带阴影的天光。

**Final Gather**（`Lumen` / `Lumen.Translucency` / `Lumen.TranslucencyVolume` / `Lumen.DiffuseIndirect`）：在 Final Gather 阶段把上述全部合成并**"应用"照明到表面**，产出可被后续 pass 直接使用的结果（如 translucency lighting texture），用于低分辨率场景照明与 distant light cache。追踪来源可为 `SurfaceCacheOnly` / `ScreenProbeGather`（先屏幕空间 probe gather，miss 再回落到 Global SDF + Lumen Scene）。硬件光追 Lumen 可额外提供 ReSTIR 采样。

### 4.3 Clustered Forward / Deferred / Forward+ / GoRD

| 方法 | 成本 | 光照量 | 半透明 | 场景 |
|---|---|---|---|---|
| Forward | O(objects × lights) | 少 | 是 | 简单场景、移动 |
| Deferred | O(objects + lights) | 多 | 否 | 复杂场景、多灯 |
| **Forward+**（分块 tiled） | O(objects + tiles × lights) | 多 | 是 | 兼顾两者 |
| **Clustered Forward** | O(objects + clusters × lights) | 非常多 | 是 | 现代 AAA 标准 |

- **Clustered Forward**（Filament / Godot Forward+）：视锥切成 3D 视锥对齐网格（Filament 叫 **Froxelizer**，frustum-shaped voxel），cluster 而非屏幕 tile——这是它能在 VirtualXR / 分辨率无关下正确工作的原因。
- **GoRD**（GPU-oriented Rendering，Ubisoft Anvil）：内容按材质/复杂度聚成 batch，把 shader 与资源状态变化推到**批边界**，让 GPU 内核与驱动看到更长的同质工作段。本质是「面向 GPU 而非面向 CPU 的调度」。
- **Godot 的实现选择**：Forward+ 与 Mobile 都支持最多 8 个平行光同时生效（多于一盏带阴影时阴影质量下降）；Forward Mobile 每Mesh 限制 8 Omni + 8 Spot（相机视野内总计 256 + 256）；Compatibility 用「单 pass + 多 pass」混合——无阴影光单 pass 一把画完，`DirectionalLight3D` 带阴影时首 pass 可画多盏无阴影光 + 至多 1 盏带阴影平行光，之后每 pass 一盏 Omni + 一盏 Spot + 一盏带阴影平行光。性能随带阴影灯数**非线性劣化**，故建议同屏只留少量分散的投影灯。三种方法都支持反射探针（Compatibility 除外）与 decal（Compatibility 除外）。

### 4.4 Temporal AA / Upscaling

**FSR 2（TAAU，替换 TAA）** 的完整 pass 序列（`FfxFsr2Pass` 枚举，注意部分枚举值互斥，由 `ffxFsr2ContextDispatch` 的 dispatch 参数与 context 创建方式决定选用哪个）：

| 枚举值 | 通道 |
|---|---|
| `FFX_FSR2_PASS_DEPTH_CLIP` = 0 | 深度裁剪 |
| `FFX_FSR2_PASS_RECONSTRUCT_PREVIOUS_DEPTH` = 1 | 上帧深度重建 |
| `FFX_FSR2_PASS_LOCK` = 2 | 像素锁定 |
| `FFX_FSR2_PASS_ACCUMULATE` = 3 | 上采样/累积 |
| `FFX_FSR2_PASS_ACCUMULATE_SHARPEN` = 4 | 上采样+锐化 |
| `FFX_FSR2_PASS_RCAS` = 5 | 锐化 |
| `FFX_FSR2_PASS_COMPUTE_LUMINANCE_PYRAMID` = 6 | 生成当前帧亮度 mip 链 |

以及 `DRAWMARK`, `PREPASS`, `DRAWINDIRECT`, `REJECTION`, `BICUBIC`, `STABILITY`, `UPSAMPLE` 等 pass（官方 README「The technique / Algorithm structure」章节列出：Compute luminance pyramid → Adjust input color → Reconstruct & dilate → Depth clip → Create locks → Reproject & accumulate → RCAS）。源码在 `src/ffx-fsr2-api`：`ffx_fsr2.cpp`（前端）、`dx12/ffx_fsr2_dx12.cpp`、`ffx_fsr2_vk.cpp`（后端）、`shaders/`（体量很大；GLSL 相关集中在 `ffx_fsr2_callbacks_glsl.h`）。

**质量档与抖动序列长度**：0 = 1.0（原生，仅 AA）16 帧；1 = 0.6667（Quality）18 帧；2 = 0.5882（Balanced）23 帧；3 = 0.5（Performance）32 帧；4 = 0.3333（Ultra Performance）72 帧。

**算法机制**（AMD GDC 2023）：
- **相机抖动**：必须在渲染前修改相机矩阵，让每帧在渲染分辨率像素内采样不同位置。推荐 **Halton(2,3) 序列**。抖动序列质量是关键（空间+时间分布都好）。
- **Lanczos 重采样**：`Lanczos(x)` 参数 `a` 可调锐度；虽是 ALU 密集但可 LUT 化（若受内存带宽限制）。**重投影步骤不可用近似**，否则出现明显artifact。解决振铃：clamp（`P` 为高分辨率采样，`S` 为低分辨率采样集，`ω_s = Lanczos(β|PS|)`，`Ω = Σω_S`，`P = (1/Ω)·Σ(S·ω_S)`；`β` 为基于时域稳定性的锐度偏置）。
- **运动向量**：屏幕空间 2D 向量，**必须把抖动抵消掉**（静止时必须是零向量）。为正确跟踪边缘，使用 3×3 邻域中最近像素的向量——这称为 **dilation**。
- **历史可靠性**（FSR 2 团队最初被"雪花/半透明/反射/动画纹理"折磨出的部分）：`depth clip` 与 `color clamp` 修复 ghosting。深度 clip 权重不依赖 motion vector，只要当前 depth 与某处 reprojection 的 depth 不同就施加权重。`AccumulationPassCommonParams` 关键字段：`presentTexel`、`presentCoord`、`renderSampleCoord`、`velocity`、`reprojectedCoord`、`texelMotion`、`depthClipFactor`、`dilatedReactiveFactor`、`accumulationMask`、`isResetFrame`、`isExistingSample`、`isNewSample`。`RectificationBox`（`boxCenter`、`boxVec`、`aabbMin/Max`、`boxCenterWeight`）由上采样阶段计算，供 `RectifyHistory()` 把历史色约束在方差邻域内。混合权重 `α = max(Ω,0)/τ`，`τ` 每帧估计（依据 deocclusion、velocity、shading change）。**Reactive Mask** 是可选输入，用于深度/运动向量无法描述的场景（粒子、合成特效、反射），强烈建议生成使用；样例里粒子做法是 `reactive[did.xy] = min(1.0f, length(particleInput)*8.0f)`。
- **其他集成要求**：可读深度缓冲、游戏运动向量、`ffxFsr2DispatchDescription` 提供 `frameTimeDelta`（毫秒）；子像素抖动需应用到投影矩阵；支持自定义渲染分辨率（`CUSTOM_RENDER_RESOLUTION` 时用 `RedoProject()` / `RedoProjectDH()`，后者为LOD / Distant Horizons 集成）；mip biasing；HDR 输入（不支持时回落 32 位浮点）；**64-wide wavefront** 部分通道需要 `CS_6_6`（否则 `CS_6_2`）。

**架构模式（值得独立借鉴）**：FSR 2 API 的核心算法**不知道**自己坐在哪个渲染 API 上，而是通过 `FfxFsr2Interface` 回调调用宿主提供的函数（`FfxFsr2ScheduleGpuJobFunc` 等）。因此：① 官方只发 DX12 与 Vulkan 后端，但**任何平台**都能实现「几个函数」的自定义后端；② **已有自己渲染抽象的引擎可以实现自己的后端**，接管内存管理、资源创建、着色器编译、SRV 绑定、dispatch 提交的**全部**控制权；③ API **不做任何动态内存分配**（资源全部用宿主给的 device 以 committed resource 创建），销毁 `FfxFsr2Context` 前**不做隐式同步**，要求 GPU idle——刻意避免在宿主已充分同步的点上再引入 GPU flush。**这正是「可扩展 GPU 方案」最干净的落地形态：算法与 API 解耦 + 回调表注入。**

### 4.5 Bindless / GPU Scene / SBT

**Bindless**：把全部资源放进一个巨大的描述符堆/表，shader 用**运行时计算的句柄**索引，而非每个 draw 绑定固定槽位。

```glsl
#version 450
#extension GL_EXT_nonuniform_qualifier : require
layout(set = 0, binding = 0) uniform sampler2D textures[];  // bindless 数组
layout(push_constant) uniform PushConstants { uint texture_index; } pc;
layout(location = 0) in vec2 uv;
void main() {
    vec4 color = texture(textures[nonuniformEXT(pc.texture_index)], uv);
}
```
CPU侧：注册一次拿句柄；每 Mesh 只上传一个 `uint`；绘制时只 `vkCmdPushConstants` 一个 uint，**无需 per-object 绑定调用**。

- **优势**：消除 per-draw 绑定开销（可支撑百万级 draw call）；单一 shader 处理数千种资源而**不产生变体爆炸**；简化多线程渲染（不再依赖 per-thread 绑定状态）；shader 内可动态选资源（LOD 选择、细节混合）而无需 CPU 介入；降低 D3D12/Vulkan 驱动状态切换与校验开销。
- **代价**：需显式内存管理（句柄 in-flight 期间资源不可删）；handle 间接增加指令数与潜在 cache miss；老 GPU 无支持需回落路径；**调试更难**（要靠应用层日志才知道句柄指向谁）；CPU/GPU 时间线的资源生命周期同步需格外小心。
- 相关：ARB_bindless_texture（传统 OpenGL，64-bit 纹理句柄）、**Persistent Descriptor Heaps**（描述符堆不逐帧重建，降低驱动开销）、**Sampler Array Heaps**（采样器独立堆）。UE 5.5 把 bindless 扩展到更多平台，完整集成 DX12/Vulkan/Metal。Nanite 用 bindless 渲染数百万 unique mesh instance 并保留 per-instance 材质参数，**复用同一 shader**。

**光追管线：五个 Shader Stage**（DXR 与 Vulkan RT 共有）：RayGeneration（入口与首次发射）、Miss（未命中任何 primitive）、Intersection（自定义求交算法，多数情况用默认）、AnyHit（命中透明几何）、ClosestHit（最近命中）；后三者组成 **HitGroup** 提交。

**SBT（Shader Binding Table）**：光追管线**无法预先确定「哪条射线」会与「哪个几何的哪个图元」相交**，因此必须把所有几何会用到的着色器与资源**整体**交给管线。**DXR 与 Vulkan 都没有专门的 SBT 类/结构体，都把 SBT 当普通 buffer**——因此 SBT 的内存与布局管理**完全由应用负责**。SBT 是由多个 entry 组成的连续内存块，每 entry = 着色器句柄 + 该着色器可用的资源/常量数据。**资源部分是 DXR 与 Vulkan 的最大差异之一**：DXR 映射为 **local root signature → 小 SBT local data**；Vulkan 映射为**描述符索引 + 描述符数组**，或经 `VK_EXT_descriptor_buffer` 直接映射。

**DXR ↔ Vulkan 概念映射**：

| DXR | Vulkan 对应 |
|---|---|
| 着色器标识符 `GetShaderIdentifier` | `vkGetRayTracingShaderGroupHandlesKHR` 句柄 |
| local root signature | SBT local data + 描述符索引 / `VK_EXT_descriptor_buffer` |
| `InstanceContributionToHitGroupIndex` | `VkAccelerationStructureInstanceKHR::instanceShaderBindingTableRecordOffset` |
| AS 的 UAV 屏障 | `VK_ACCESS_ACCELERATION_STRUCTURE_WRITE_BIT_KHR` + 合适的 pipeline stage |

跨 API 可移植性经验法则：让着色器组的**排序与命名跨管线稳定**，使 SBT 生成器能复用同一映射表；把绑定模型抽象成「引擎级绑定描述符 → 平台特定资源绑定器」；**共享着色器源码**——HLSL + DXC 生成 DXIL（给 DXR）与 SPIR-V（给 Vulkan），把源码分歧降到最低。

**两种 UE5 光追模式**（容易被误解的分岔）：
- **Ray Tracing Shaders（传统）**：专用 RayGen/Miss/Hit Shader，经 SBT 调度，功能完整（材质着色、任意 Hit Shader、RTXDI）。要求 DXR 1.0 / Vulkan Ray Tracing。
- **Inline Ray Tracing（内联）**：在 compute shader 里直接调 `TraceRay` 内联函数，**不走 SBT**。功能受限但**开销更低**，且**不需要编译 Ray Tracing Shader 变体**。要求 DXR 1.1（SM 6.5+）/ Vulkan `rayQueryEXT`。Lumen HWRT Surface Cache 模式默认用 Inline。
- **InstanceInclusionMask + RayFlags 位与**决定「这条光线能命中哪些实例」：阴影光追只与 Opaque + ThinShadow 相交，半透明反射只与 Translucent 相交，Path Tracer 打开所有位。这是 **BVH 遍历时的硬件加速路径**，不用扫全表也不用查 SBT。另有一条特殊逻辑：Path Tracer 打开时**强制禁用剔除**（任何剔除都会让离屏对象的反射消失，破坏路径积分正确性）。

### 4.6 物理 → 渲染的跨域耦合（与 arch-ecs-physics 联合调研）

帧图把「谁来写变换」抽象掉了，但**变换从哪来**是渲染侧无法回避的输入契约。以下 5 条来自 ECS/物理侧的实测结论，每条都会在渲染管线里留下可观测的痕迹。

#### 4.6.1 增量同步：只传「本步真正动过」的物体

物理侧普遍提供**增量**接口而非全量遍历：Rapier 的 `world.islands.active_bodies()` 只返回**本步真正动过**的刚体；Jolt 的接触缓存是**双缓冲**（读缓存是上帧的、写缓存是本帧的），`Update()` 末交换。

对渲染的含义（这是最容易写错的地方）：

```
❌ 每帧遍历全部 10 万刚体 → 重算世界矩阵 → 全量上传
   → 抵消掉物理本身省下的全部时间；且 GPU Scene 的上传带宽被无意义地打满

✅ 只同步 active_bodies：
   for body in world.islands.active_bodies():
       prev_matrix[id] = current_matrix[id]      # ← 见 4.6.2，必须先存
       current_matrix[id] = body.world_transform()
       dirty_instances.add(id)
   upload(dirty_instances)   # 局部上传，而非整块
```

**推广到渲染侧**：GPU Scene 的 per-instance 数据（§5 步骤 [0]）应当是**增量上传**的。这与 Nanite 的 cluster 级流式加载、Godot 的不可变资源免跟踪，是同一条设计哲学的三个实例——**把「全量、无差别」换成「增量、已知脏集」**。

#### 4.6.2 `prev_transform` 是 TAA/运动模糊的硬前提

走 ECS 组件路径（如 `LocalToWorld` 组件）时，**必须同时维护 `prev_transform`**。否则物理的**步进式更新**（step-based，而非连续插值）会丢失帧间位置差 → **运动向量全错** → TAA / FSR2 的历史重投影失效 → 表现为拖影、ghosting、边缘闪烁。

物理侧的三种对应机制：

| 引擎 | 机制 | 渲染侧对应 |
|---|---|---|
| Bullet | `saveKinematicState(timeStep)` 保存运动学体状态；`m_latencyMotionStateInterpolation`（默认 true）做延迟插值缓冲 | 渲染端对应「上一帧位置」的延迟可用 |
| Jolt | `MotionProperties`（可与 `Body` **分离存储**） | 运动学数据可独立于刚体存放，便于 ECS 侧另存一份 prev |
| Rapier | `active_bodies()` 增量 | 只对增量集合做 prev 更新 |

注意 Jolt 把 `MotionProperties` 与 `Body` 分离这一点对**内存布局**有实际影响：ECS 的 `LocalToWorld` 组件可以做成「当前 + prev」双缓冲结构，也可以只存 `MotionProperties` 引用、在渲染侧解引用。

**与 §4.4 的直接咬合**：FSR2 的运动向量必须**抵消相机抖动**（静止时必须是零向量），这意味着运动向量要**剔除**抖动分量。反过来说，如果 `prev_transform` 本身已含抖动或与之不同步，抵消逻辑就会引入残余误差——这正是 FSR2 团队踩过的「雪花」类 artifact 的一种来源。

> **注意区分两类问题**（初版在此处把它们混为一谈）：`prev_transform` 缺失是**正确性**问题（运动向量全错，每帧都错）；而 §4.6.4 讨论的确定性是**稳定性**问题（同输入是否得到同输出）。**前者与确定性无关**——即使物理 100% 确定，忘了维护 `prev_transform` 照样会得到完全错误的运动向量。两者的排查手段不同：前者看单帧的运动向量是否正确，后者看两次运行的结果是否逐位相同。

#### 4.6.3 浮点精度：离原点越远越不精确

Jolt 明确把这条写进注释：`NarrowPhaseQuery::CollideShape` 的 `inBaseOffset` 参数让所有命中结果**相对于该偏移**返回。核心事实是——**浮点在原点附近最精确**。在远处做碰撞测试时，选一个更接近原点的基准位置（如 `inCenterOfMassTransform.GetTranslation()`）能显著提升精度。

对渲染的三处直接影响：

1. **大世界场景的相机远离原点** → 顶点/位置数据用绝对 float 存储会抖动。渲染侧的对应手段是**浮动原点（floating origin）**或 double-precision 位置缓冲。
2. **Nanite 的 cluster 局部编码**（§4.1）——cluster 内顶点相对 cluster 原点存储，正是这个原理的实例化应用：**用局部基准换绝对精度**。
3. **Lumen 的 Global Distance Field**（§4.2）——SDF 体素网格在远世界同样受精度限制，这是 Lumen 距离场方案本身的精度上限来源之一。

**结论**：物理侧选 `inBaseOffset` 的理由，与渲染侧选「cluster 局部原点」的理由是**同一条**——把计算基准挪回数值精度高的区域。两者应在设计文档里对齐，否则会出现「物理认为相撞、渲染认为没动」的分裂。

#### 4.6.4 确定性：四条轴，与渲染侧的真实风险点

> 本节已按 arch-ecs-physics 的澄清重写。初版把「确定性」当成单一维度并据此推出时域放大风险，**该推论的前提被证伪**（见下）。

确定性其实沿**四条独立的轴**成立，物理库对每条轴的覆盖度不同：

| 轴 | 含义 | Box2D | 破坏来源 |
|---|---|---|---|
| **A 算法确定性** | 同 binary、同输入 → 同输出 | ✅ | 对象池 free list |
| **B 多线程确定性** | 跨线程数仍一致 | ✅ | 线程相对速度、OS 调度、atomic 顺序 |
| **C 跨平台确定性** | 跨 CPU / 编译器 | ✅ | fast-math、FMA（`-ffp-contract=off`）、三角函数（`atan2f` 跨平台确实给不同结果，必须自实现近似版）；反例：`sqrtf` 在 x64 落到 `sqrtss` 指令天然确定 |
| **D 回滚确定性** | 网络重放 / 状态回退 | ❌ **不支持** | 内部状态过多，无回滚机制 |

**修正我自己的推论**：初版写「确定性差异在渲染侧会被时域放大」，前提是同平台跨运行会不一致。实际上 **A 和 B 都被保证**（Box2D/Jolt 皆然），同平台跨运行本来就一致，因此**「TAA/FSR2 历史缓冲递归累积」的担忧在物理侧已被消掉**——运动向量的输入是确定的，历史累积不会自行发散。

**真正未覆盖的只有 D（回滚）**，而这恰恰是物理选型时的硬约束：Box2D **不能用于 lockstep 网络同步的确定性重放**（作者明说内部状态过多且无回滚机制）。

> **D 轴对渲染侧同样有直接后果**：D 缺失意味着**无法把「回到某个历史时刻重算一帧」作为调试手段**。而这恰恰是渲染调试最常用的招——把相机挪到可疑位置、回退若干帧看 artifact 何时出现。物理层没有回滚能力时，这条调试路径整个失效：只能靠「从初始状态重跑一遍」来近似，而这在有随机源（见下）时又不成立。**若一个引擎把「帧回退」列为渲染调试特性，物理层的 D 轴必须支持**，否则该特性只是宣传。

**但「库级 flag 骗人」这条仍然成立，且是渲染侧更该防的**。Rapier 官方文档在 `enhanced-determinism` 后带限定条件：**"assuming the rest of your code is also deterministic"**——该 feature **只保证 Rapier 库内部确定**，实际破坏源在调用方：

- Rust `HashMap` 默认 hasher 用**随机种子**（SipHash，per-process 随机化），**迭代顺序跨运行不同**；
- `parallel` feature 走 rayon，**work-stealing 的归约顺序本身是不确定性来源**。

所以「`parallel` + `enhanced-determinism` 同时开」在**库内**自洽，但只要你的迭代路径碰到一个**无序容器**就破了。这比跨平台差异更常见、更隐蔽。

**给渲染侧的可操作判据**（本节最实用的一条）：

> 若要做跨平台帧一致性验证，**光比对跨平台结果不够，还要同一 binary 跑两遍比对**。
> 库级 flag 能骗过跨平台测试，说明破坏源在**调用方代码**——而调用方恰恰是渲染侧自己写的遍历逻辑。

这条判据的推导：跨平台测试通过 ⇒ C 轴成立；同 binary 跑两遍也一致 ⇒ A、B 轴成立。**三者都过，才能断定「时域累积会递归放大」这个风险不存在**。少跑任何一项都是在给一个未验证的假设背书。

**对帧图编译的确定性要求（仍然成立，但理由要换）**：

- 帧图编译阶段的排序必须**全序或确定性的偏序**，不得依赖未加约束的浮点相等。
- UE5 RDG 明确「graph builder API 是单线程的，同一时刻只能有一个实例，**不支持层级图或并列图**」——这个限制**买到的不只是 pass 排序的确定性，还包括 pass 资源别名分析的确定性**：**别名消除是顺序敏感的**，两个 pass 能否复用同一块显存取决于遍历序。单一 builder 天然消除了这两类歧义。

> 把「不支持层级图」读成单纯的实现偷懒会低估它——它同时消除了**排序歧义**与**别名歧义**两类。

#### 4.6.5 复合碰撞体的内部边：静态几何合并的坑

Jolt 提供 `CollideShapeWithInternalEdgeRemoval`，用 `InternalEdgeRemovingCollector` 消除**复合形状内部相邻子形状**本不该碰撞却报出的接触。

**渲染侧的对应场景**：做静态复合碰撞体（merged static geometry）时若采用「把多个子形状拼成复合体」的简化，内部的相邻子形状会互相报接触。这会让「本步动过的物体」集合**膨胀**——**直接污染 §4.6.1 的增量同步**（大量本不该更新的物体进了 dirty 集），进而放大 §4.6.2 的 `prev_transform` 维护成本与 §4.6.3 的精度风险。

**一条贯穿的教训**：物理侧的「增量物体集合」是渲染侧「脏数据上传集合」和「prev 矩阵维护集合」的**唯一上游**。上游的膨胀会沿着这条链一路放大到 GPU 带宽。**过滤粒度必须在物理侧就收紧**。

## 5. 一帧的完整生命周期

把上面的机制拼成一条管线（以 Godot Forward+ / UE5 deferred 类前向聚簇管线为骨架，标注各层归属）：

```
[0] CPU：帧准备
    ├─ 物理步进 → 得到「本步真正动过」的物体集合（Rapier: islands.active_bodies()）
    │   └─ 仅对该集合：prev_matrix[id] = current_matrix[id]   ← prev 必须在覆盖前存
    │                  current_matrix[id] = 新世界矩阵
    │                  dirty_instances.add(id)
    │   ⚠ 若不维护 prev_matrix，帧间位置差丢失 → 运动向量全错 → TAA/FSR2 失效
    ├─ 更新场景 ECS（Filament TransformManager / Godot Scene）→ 上传 uniform buffer
    ├─ GPU Scene 上传：仅 dirty_instances 的 per-instance 变换 + 材质索引 + bindless 句柄
    │   → 增量上传到 storage buffer（不是每帧全量）
    ├─ 阴影：Cascaded Shadow Map / VSM 深度渲染（用上一帧可见性集合）
    └─ Lumen: 重新捕获附近网格的 Card → 写 Surface Cache 图集（摊销，每帧 ~4 次）

[1] CPU：录制帧图（SETUP 时间线 / 声明阶段）
    GraphBuilder = FRDGBuilder(RHICmdList)   // 或 Godot RenderingDevice 的 command 列表
    Depth   = GraphBuilder.CreateTexture(R32F, 用途含 Depth|Texture)   // 瞬态，可别名
    VisBuf  = GraphBuilder.CreateTexture(R64_UINT, 用途含 Texture)    // Nanite
    Color   = GraphBuilder.CreateTexture(RGBA16F)
    Velocity= GraphBuilder.CreateTexture(RG16F)
    Cluster = GraphBuilder.CreateTexture(...)                          // 光聚簇
    SurfaceCache = GraphBuilder.RegisterExternalTexture(...)           // 导入，不别名
    GraphBuilder.AddPass(RDG_EVENT_NAME("Opaque"), Params{RENDER_TARGET_BINDING_SLOT(VisBuf),
                                                          SHADER_PARAMETER_RDG_TEXTURE(Depth)},
                         ERDGPassFlags::Raster, Lambda)

[2] CPU：编译帧图（纯 CPU，无 GPU 工作）
    ├─ 拓扑排序
    ├─ 死 pass 剔除（从输出反向可达性 / 引用计数）
    ├─ 生命周期扫描 → 内存别名 → 跨帧池化（瞬态分配器按 2 的幂 bucketing）
    ├─ 屏障计算：SRV↔RT / RT↔UAV、split barrier begin/end、异步 compute fence
    └─ Godot 额外：不可变资源跳过跟踪 → 只跟踪被写入的 mip
    # 结果：一棵带屏障标注的执行序 + 一组物理分配决策

[3] GPU / 渲染线程：执行帧图（EXECUTE 时间线，可多线程并行）
    ├─ [L1] 阴影深度渲染 → ShadowMap（可并行）
    ├─ [L0] 光聚簇 compute：把光分到视锥对齐 grid（Filament: Froxelizer）
    ├─ [L1] Nanite：视锥剔除 → HZB 两遍遮挡剔除 → LOD 选择 → 写 VisBuffer(64-bit atomic)
    ├─ [L2] 深度预通道
    ├─ [L3] 几何/材质分类：cluster → material，按材质分bin（NaN 排序技巧处理透明）
    │        ↑ 批次边界的本质是「状态变化点」：Cocos2d-x 的 CPU 侧合批按 materialID 切批（§2.5），
    │          与 Nanite 的「按材质分bin」是同一思路的两种粒度
    ├─ [L4] Opaque 着色：延迟材质求值（只对可见像素）+ IBL + 聚簇光照
    ├─ [L4] Draw Sky
    ├─ [L5] 半透明（Forward+/Mobile 支持，Compatibility 不支持）
    ├─ [L5.5] 运动向量生成：Velocity = (current_matrix - prev_matrix) 投影到屏幕空间
    │          ⚠ 依赖 §4.6.2 的 prev_matrix；且必须抵消相机抖动分量
    │          ⚠ 3×3 邻域 dilation（取最近像素的向量）——FSR2 明确要求
    ├─ [Lumen] Screen Trace → miss 则 World Trace(HWRT 或 SDF)
    │          → Final Gather → Lumen Scene / 光追结果回写 Surface Cache
    └─ [L6] TAA / FSR2：
             ① 抖动投影矩阵（Halton 2,3）
             ② PrePass / DrawIndirect
             ③ DepthClip（深度不连续降权）
             ④ Reconstruct & Dilate 上帧深度（motion vector dilation）
             ⑤ Lock（像素锁定）
             ⑥ Rejection（reactive mask）
             ⑦ Bicubic（Lanczos 4×4 历史重投影）+ RectifyHistory（RectificationBox）
             ⑧ Stability（spatial sort + neighbor vmax）
             ⑨ History（α = max(Ω,0)/τ 混合）
             ⑩ Accumulate + RCAS 锐化 → Present 帧
    SwapChain::commit / vkQueuePresentKHR

[4] CPU：收尾
    ├─ FrameInfoManager::endFrame；CommandStream::tick
    ├─ ResourceAllocator.gc（释放上一帧已无引用者）
    └─ 采历史可见性集合 → 供下一帧 [0] 与 [3] 的剔除使用
```

**关键不变量**（每个抽象层都在努力维持的不变量）：
1. 每条命令从合法状态出发、到合法状态结束（Godot RDG 明确声明此不变量）。
2. 用户从不写 barrier / 从不填layout（Dawn/wgpu/Godot RDG 达成此不变量）。
3. Pass lambda 内部无副作用，仅向 command list 录命令（因为可能多线程并行执行）。
4. 被剔除的 pass 不分配资源、不发屏障（UE RDG 明确）。
5. `GetRHI()` 只在 pass lambda 内合法，validation 层断言（UE RDG 明确）。
6. 帧图 builder 单线程、单实例——UE RDG 明确，因此**不支持层级图或并列图**。
7. **变换增量性**（跨域，见 §4.6.1）：CPU→GPU 的每实例数据只上传本步真正动过的集合，且该集合必须是**物理侧过滤后**的（复合碰撞体的内部边幽灵接触会污染它）。
8. **帧间位置差可得**（跨域，见 §4.6.2）：每个可动实例在任意时刻都能取到「上一渲染帧的世界矩阵」，否则时域累积（TAA/FSR2）失去前提。
9. **帧图编译确定性**（跨域，见 §4.6.4）：帧图编译的 pass 排序与**资源别名分析**都必须是确定性的（别名消除顺序敏感），不得依赖未加约束的浮点相等。注意这条是**渲染侧自身**的要求，与物理侧的 A/B/C/D 四轴无关——物理侧 A、B 已保证，渲染侧不能把这个保证当成免检通行证。

## 7. 横向提炼：八种抽象策略

| 策略 | 代表 | 核心手法 | 代价 |
|---|---|---|---|
| **隐式化状态** | WebGPU（wgpu-core / Dawn） | 记录「期望状态」而非「当前状态」，submit 时补屏障 | 必须维护完整 state 追踪表 |
| **帧图编译** | UE RDG / Filament FrameGraph / Godot RDG | pass 声明读写 → 编译期做剔除/别名/屏障 | 单线程 builder，禁层级图 |
| **隐式命令图** | Godot RDG（更激进） | 用户只录「command」，RDG 自己推 pass 与屏障；不可变资源免跟踪 | 表达力受限，控制粒度粗 |
| **算法/API 解耦** | FSR2 `FfxFsr2Interface` | 算法只调回调，后端实现资源/绑定/提交 | 宿主需实现数十个函数 |
| **GPU-driven + bindless** | Nanite / GoRD / UE5 绑无 | GPU 自己剔除与绘制，CPU 只上传一次 | 需 SM6，调试困难 |
| **增量脏集**（新增，见 §4.6.1） | Rapier `active_bodies` / Godot 不可变资源 / Nanite cluster 流式 | 只处理「真正变了的」子集，而非全量 | 上游过滤粒度必须收紧，否则脏集膨胀 |
| **后端表 + noop 兜底**（新增，见 §2.4） | bgfx `s_rendererCreator` | 运行期查表选后端；**11 槽位恒定**，索引 0 恒为 noop 且 `supported=true`；`static_assert` 锁表长与枚举数一致 | 抽象层不管状态管理，barrier 交给各后端 |
| **枚举边界编码时序**（新增，见 §2.4） | bgfx `CommandBuffer::Enum` 的 `End` | 用一条枚举的边界把「创建 / 使用 / 销毁」切成 pre/post 两段，销毁自动推迟到 submit 之后；`End` 一值两用（分界 + 终止符） | 队列编排灵活性下降（对比 SDL3 的依赖检测式） |

**最值得直接借鉴的七条**：
1. **`FfxFsr2Interface` 式回调注入**——让任意效果算法零成本落到任意已有 RHI 上，且不引入动态分配与隐式 flush。
2. **Godot 的「不可变资源免跟踪」**——在屏障自动化里引入「创建后不变」这一性质，可把状态追踪范围从「所有纹理所有 mip」缩到「被写入的 mip」，是纯粹的复杂度削减。
3. **`Tracker` 的「期望状态 + submit 时补齐」模型**——在允许并行录制、任意顺序 submit 的前提下消除 barrier 类 bug，且不需要用户写任何同步代码。
4. **「增量脏集」贯穿三域**（物理 → 变换 → GPU 上传）——同一个「只处理真正变了的子集」原则，在 Rapier 的 `active_bodies`、Godot 的不可变资源免跟踪、Nanite 的 cluster 级流式加载里是**同一条**设计哲学。差别只在过滤依据：物理侧是「本步动过」，资源侧是「创建后不变」，几何侧是「屏幕尺寸够大」。**这条原则的失败模式也相同——上游过滤放宽，下游成本线性膨胀。**
5. **bgfx 的「后端表恒长 + noop 结构性保证」**——新增后端时表长不变、平台不适配时退化为最小可用实现而非编译失败或崩溃。配套的 `static_assert(表长 == 枚举数)` 把「加后端忘加枚举」变成编译期错误。**这是可插拔抽象最省事的形态：一张表 + 一个静态断言 + 一个兜底后端**（且兜底后端位于索引 0 且 `supported = true`，使「至少一个后端永远可用」不依赖任何 `#if`）。
6. **bgfx 的「枚举边界编码时序」**——用 `CommandBuffer::Enum` 里一个 `End` 标记把命令切成 pre/post 两段，`Context::renderFrame` 按 `cmdPre → submit() → cmdPost` 执行，**销毁类命令天然被推迟到 GPU 用完之后**。把时序约束编码进类型，比用运行期标志位更不容易写错。**且 `End` 一值两用**（既是 pre/post 分界，又是批次终止符），省掉一个独立枚举。
7. **两种资源释放时序保障的取舍**（见 §2.4 对照表）——**要「写不错」抄 bgfx**（枚举边界，结构性保障），**要「灵活」抄 SDL3**（运行期按 generation 依赖检测，允许动态编排队列）。SDL3 方案漏更新 `last_command_generation` 会 use-after-free。

**另有一条纯工程约束（非架构范式，单列避免混淆）**：

8. **接口基类标 `__declspec(novtable)`**（MSVC 专属）——该属性停止生成**构造/析构中的 vfptr 初始化代码**，使链接器可回收该类关联的 vtable，**多后端时代码体积收益可观**。MSVC 文档明确**要求该类为纯接口类**（绝不被单独实例化，否则访问成员会 AV）。`RendererContextI` 40 个纯虚、不可实例化，用法与要求完全匹配。**注意这是代码体积优化，不改变虚调用机制**（调用点仍是标准虚调用 + `override`）；且 bx 的 `BX_NO_VTABLE` 在 **GCC/Clang 下展开为空**，只在 MSVC 生效。
