# P3-a 帧图（Frame Graph）设计说明

> 轨道：**P3 帧图管线**。本批是 **P3-a：内核 + 编译期校验 + 门禁**；
> **P3-b（图驱动渲染的 demo）见 `docs/P3-b_帧图驱动渲染_design_note.md`** —— 已交付。
> 相关：`engine/framegraph.py` · `cli/frame_plan.py` · `tests/test_framegraph.py`（16 项）·
> CHANGELOG「P3-a」段。

## 1. 为什么引擎化到最后一定要有它

④ 轨道攒下四个效果（CSM / 体积雾 / 景深 / 运动模糊），它们**互相共用资源**：
三者都用同一张"线性距离"图，阴影图又给体积雾的单次散射查。于是"谁先谁后"不再是
可以随手写的 —— 顺序错了会**静默出错**（画面"有点不对"，但不报错、不崩）。

这些约束写在注释里迟早会漂。`engine/framegraph.py` 把它们变成**数据结构 + 编译期校验**：
声明"每个 pass 读什么、写什么"，`compile()` 负责校验、剔除、排序、别名。

## 2. 三条被钉住的判据

| # | 判据 | 为什么它值得钉 |
|---|------|---------------|
| 1 | 执行顺序 = `depth_prepass → shadow → scene → **fog → dof → motionblur** → tonemap → present` | **雾 → 景深 → 运动模糊是有物理依据的**：雾是"光在介质里被散射"，它产生的像**也要被虚化**；运动模糊是**曝光积分**，拖影要拖"已经虚化的像"。这条写进 `SEQUENCE_OF_DEPTH_EFFECTS`，**门禁 `cli/frame_plan` 会红** |
| 2 | 关掉效果的收益必须是"**少跑一个 pass**" | 关 0/1/2/3 个效果 ⇒ pass 数 **8 → 7 → 6 → 5**（测试里是一条硬的阶梯断言）。而不是"跑一遍但不用结果" |
| 3 | 读不到生产者 / 有环 / 计划为空 ⇒ **编译期报错** | 这三种情况在运行期都表现为"画面全黑或怪"，极难定位；在编译期它们是一行错误信息 |

## 3. 关键设计决策

| # | 决策 | 理由 |
|---|------|------|
| 1 | 帧图**纯逻辑**（不 import GL） | 与 ④ 四个模块同一个套路：**把会写错的部分抽出来，让它可测**。16 项测试全在 headless 下跑 |
| 2 | 死 pass 用"**从输出反向遍历**"剔除，而不是"正向找没人读的" | 一个 pass 可能自己没人读、但它写的东西被另一个死 pass 读 —— 反向遍历一次搞定 |
| 3 | `present` 标 `side_effect=True` | 它不写资源（写的是屏幕），不标就会被正确剔除 —— 这条**反例也在测试里**（不标 ⇒ 确实被剔） |
| 4 | 运行期开关用 `disable()` → **输出直通到第一个输入** | 这才是"关掉效果的收益"的实现方式：中间那张纹理**不再需要**，会被别名回收 |
| 5 | 重定向链**解析到不动点** | 三个效果一起关时链是 `hdr_mb → hdr_dof → hdr_fog → hdr`。**只映射一层 ⇒ 关单个没问题、关三个才炸**（本轮实踩） |
| 6 | 别名只对**生命周期不重叠**的瞬时资源；判据用**严格小于** | "读 A 写 B"的同一个 pass 里 A 与 B 是**共活**的 ⇒ 不许别名。半开区间取 `hi < lo` 而不是 `hi <= lo` |
| 7 | 平级 pass 按**声明顺序**（不按字典序） | 否则"换个名字顺序，执行顺序就变"，帧间稳定性无从谈起 |
| 8 | 纯生产者 pass（如 `shadow_pass`）只能**建图时**决定开不开 | 它不读任何东西、没有上游可直通 ⇒ 运行期 `disable` 会被内核拒绝。这条约束是*对的*（硬关它下游就没数据），门禁 `cli/frame_plan` 因此对两种关法分别处理 |

## 4. 与既有件的关系

| 件 | 关系 |
|----|------|
| `engine/csm.py` / `volumetrics.py` / `dof.py` / `motionblur.py` | 帧图把它们的 pass 排在一条线上；三者的 GLSL **已由测试验证能拼进同一片段**（21 个 uniform） |
| `cli/config_boot.py` | 同风格的门禁 CLI：`python -m cli.config_boot all` 验配置树，`python -m cli.frame_plan --all-toggles` 验帧图**16 种组合** |
| `host/tree.py` | 配置树管"有哪些服务"，帧图管"这一帧跑哪些 pass" —— 一个管装配、一个管每帧的调度 |

## 5. 已知不足 / 下一步（P3-b）

1. ~~还没有"图驱动渲染"的 demo~~ → **P3-b 已交付**（`examples/frame_graph.py`）：
   渲染循环遍历 `plan.order`、目标按资源声明创建、输入按 `plan.reads_of()` 绑定。
   过程中发现计划必须暴露 **`resolved` 读写** —— 见 P3-b 的说明；
2. **别名只算不用**：计划会报出"哪些资源可共用内存"，但真实的内存复用要交换 FBO 的纹理
   （或用 `glTextureView`），本批没做；
3. **没有异步/多队列**：单队列顺序执行，没做 compute/graphics 并行；
4. **没有 barrier / 资源状态跟踪**：GL 层面大部分隐含同步，本批不涉及；
5. **`size` 目前只是元数据**：`'screen'` / `'half'` / 显式尺寸没有被真正用于分配 ——
   P3-b 建 FBO 时会真正用到。
