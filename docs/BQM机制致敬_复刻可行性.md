## 1. BQM 是什么（事实与归属）

- 全名 **BQM — BlockQuest Maker —**，中文《砖块迷宫建造者》；
  开发 **Wonderland Kazakiri inc.**（日本），发行 Gamirror Games / idealCat / Gamera Game；
  Steam 2018-07-26、Switch 2018-12-27、Android/iOS；国服由**腾讯极光计划**代理。
- 荣誉：2018 Google Indiegame Award（日本）**TOP10**；Steam 评价「多半好评」。
- 一句话：**"地牢编辑 + 挑战别人造的迷宫"的 8bit 砖块风解谜 RPG**，被誉为"这哪是游戏，分明是个关卡引擎"。
- ⚠️ **它是商业 IP，且带官方服务器与金币经济** —— 这条决定了下面 §2 的边界。

## 2. 合规边界（**最重要的一节**）

| 项 | 能做 | 不能做 |
|----|:----:|:------|
| **玩法机制**（推箱、开关、门、陷阱、机关组合） | ✅ 机制不受版权保护，可自研实现 | — |
| **编辑器范式**（点选元件、堆积木式摆放、开关↔门"连接"） | ✅ 抽象思路可借鉴 | ❌ 照搬其编辑器界面/图标/布局 |
| **美术/音效/字体/UI** | ✅ 全部代码程序化生成（本项目本就零素材） | ❌ 使用或临摹其素材、8bit 音效采样 |
| **名称与标识** | ✅ 自创名（**不要**用"砖块迷宫建造者""BQM""BlockQuest Maker"） | ❌ 沿用其名与 Logo |
| **关卡数据** | ✅ 自制关卡包 | ❌ 抓取/转存其官方或玩家关卡 |
| **联网分享 + 金币/入场费经济** | —（本就不做） | ❌ 复刻其经济与服务器体系 |

处理原则与既有惯例一致：**非 MIT/开放许可的参考源只读思路、不搬码不搬素材**；
文档与 README 明确标注「机制致敬 BlockQuest Maker (2018)，非移植、非复刻」。
（`examples/README.md` 里 kkrieger / nordic_saga / swarmward 等已是同一写法。）

## 3. 机制拆解（调研所得）

**基础循环**：一格一步（**同《仓库番》：只推不拉**）→ 用道具触发机关 → 开新路 → 避开致命陷阱 →
抵达出口/公主 → 或耗死重来。官方 50 关循序渐进，之后进玩家迷宫海。

**技能道具 4 种（关键设计：同一道具多种用途）**

| 道具 | 用途（多义性是其精髓） |
|------|----------------------|
| 木箱 | 压住按钮开关 / 落水当路面 / 被炸弹冲击波推开 |
| 弓箭 | 打怪（武器）/ 灭蜡烛与炸弹上的火 / **远程扳动拉杆** |
| 炸弹 | 炸可破坏墙 / 冲击波炸飞木箱 |
| 火球 | 融冰墙 / **点燃**蜡烛与炸弹 |

**场景道具**：拉杆开关（主角或弓箭可开）、按钮开关（人/木箱压住才开）、门（普通 / **金门要钥匙** /
栅栏门可穿弓箭与火焰、水上浮板可过）、陷阱（尖刺、滚石、**暗箭**、毒气、**冰面滑行**、单向导轨、移动木筏）、
怪物（史莱姆、骷髅，游荡，**身上可能带钥匙**）。

**编辑器**：绿类＝摆设（墙/地板），红类＝功能（机关/怪物）；核心机制是
**"按顺序把开关和门**连接**起来** → 开关控制门；PC 版地图可 **50×50**、**512 种道具**、
可放角色/剧情；可设免费或收费（经济部分我们不做）。

**视角**：**45° 向下 + 俯视**为主（另有几乎不用的第一人称），方块画面类似 Minecraft ——
这与我们刚给 boxward 做的**正交等距 45°** 完全同构 ✓

## 4. 可行性映射：3dworld 已有件 vs BQM 要素

| BQM 要素 | 3dworld 现成件 | 状态 |
|---------|---------------|:----:|
| 45° 等距方块视角 | `examples/boxward.py`（偏航 45° + 俯角 45°，`P` 调） | ✅ 刚做完 |
| 一格一步推箱 + 只推不拉 | `games/puzzle/kernel.py`（`PuzzleKernel` + BFS 求解器） | ✅ |
| 方块地牢 + 静态墙合批 | `core/sdf_core.py`（`SdfVoxelCore`）+ `engine/greedy_mesh.py` | ✅ |
| **关卡编辑器**（摆格/试解/导出） | boxward 的 `M` 键编辑器 + `levels/*.json`（编辑器/生成器/内核三端同 schema） | ✅ 种子已有 |
| 技能道具：炸弹 / 火球 | `core/particles_core.py`（爆炸/火焰粒子）+ `engine/postfx` | 🟡 需接玩法语义 |
| 技能道具：弓箭 | `games/fps/kernel.py`（SDF 射线 + hitscan + 弹道） | 🟡 可复用 |
| 技能道具：木箱 | 推箱本身 | ✅ |
| **开关 ↔ 门 的"连接"绑定** | `engine/orchestration.py`（事件总线 + 声明式 `when→then`，P0-5 刚自研） | 🔴 要新做（但底座已就位） |
| 门 / 钥匙 / 栅栏 | `core/inventory_core.py`（钥匙当槽位物品）+ `core/rules_core.py`（事件） | 🟡 |
| 陷阱：滚石 / 尖刺 / 滑冰 / 单向导轨 | `engine/physics.py`（AABB + 分轴解算，可做滚石与滑冰）+ `core/rules_core.py` | 🟡 |
| 怪物（游荡 + 自带钥匙）+ HP/等级 | `core/entity_core.py` + 敌人状态机（storm/fps 已有三种敌型范式） | ✅ |
| 出口/目标判定 | `core/rules_core.py`（第 6 条事件 `asset_reached` 等） | ✅ |
| 关卡包（离线"分享"） | `assets/levels/*.json`（仓库内关卡包代替服务器） | ✅ |
| 音效 / BGM | `engine/audio.py` + 程序化 SFX（`scripts/gen_sfx.py`）+ `engine/adaptive_music.py` | ✅ |
| 确定性 + headless 验收 | `cli/config_boot.py` 一族 + `scripts/run_all_tests.py` | ✅ 比同类项目厚 |
| ~~金币经济 / 矿点 / 入场费 / 官方服务器~~ | — | ❌ 不做（§2） |

**结论：渲染、视角、关卡 IO、合批、物理、实体、规则、事件、音效、验收 —— 十项全现成；
真正要新写的是「元素表 + 连接绑定 + 编辑器 UI 扩展」。**

## 5. 建议范围（MVP，自创名，例如《砖境 / Brickward》）

- **元素集（第一版 8 个）**：推箱、按钮、拉杆、门（含金门+钥匙）、炸弹、火球、尖刺、滚石、
  史莱姆（9 个，够演出"组合出谜题"）。
- **编辑器**：道具栏选元件 → 摆放 → **连接编辑**（选开关、再点门，建立 `when→then`）→
  校验（可解性 / 无孤儿连接）→ 导出 JSON。
- **关卡包**：仓库内 `levels/*.json` + 内置 10 关"官方关"（自己设计）。
- **验收**：headless 通关断言（复用 BFS/搜索求解器）+ demo `--smoke/--shot` +
  确定性回放（同关卡同输入同结果）。
- **明确不做**：联网、账号、金币/入场费、UGC 服务器、第一人称（BQM 自己都说没用）。

## 6. 分阶段路线（每阶段单独提交 + 推送）

| 阶段 | 内容 | 验收 | 状态 |
|------|------|------|------|
| **B1** 机关内核 | `games/brickward/kernel.py`：元素表（11 类）+ 一格一步确定性模拟 + **「连接」绑定（复用 `engine/orchestration.Bus`）** + BFS 求解器 + 3 个手工教学关 + 种子生成器 | `cli/config_boot brickward` → `BRICKWARD_OK`；`tests.test_brickward` 30 项 | ✅ **已交付** |
| **B2** 扩展机关与道具 | 炸弹 / 火球 / 滚石 / 史莱姆（复用 `engine/baked_mesh`、`core/particles_core`）+ 求解器强化（不可逆步剪枝、多目标） | 新元素各配单测 + 10 关全通 | ⏳ 进行中 |
| **B3** 编辑器扩展 | 道具栏 + 摆放 + 连接编辑 + 导出/导入 JSON + 校验 | demo 里编辑→试解→导出闭环保通（与 boxward 编辑器同口径） | ⏳ |
| **B4** 手感与演出 | 等距视角（复用 boxward 的 `YAW_OFFSET`/俯角）+ 方块动画 + 程序化 SFX + 导演台录一段成片 | `verify_demos` 全绿 + 录制一条成片（**攒批进发行版**，见 §7） | ⏳ |

### B1 实际交付（2026-10-13，比原计划多做了两件）

原计划把"连接绑定 + 求解器"放到 B2，实际 B1 一并交付 —— 因为**没有求解器就无法证明
"每关可解"**，而没有连接绑定就只有推箱、看不出这套内核与 boxward 的区别。B1 收口内容：

* 元素表 11 类：`#` 墙 / `.` 地板 / `P` 玩家 / `C` 箱子 / `o` 按钮 / `L` 拉杆 /
  `D` 门 / `g` 金门 / `k` 钥匙 / `^` 尖刺 / `E` 出口；
* 三类事件总线驱动 `mode = open | close | toggle` 的「开关 → 门」连接
  （`src_on` / `src_off` / `src_flip`），**每个连接只订阅它需要的那一类**；
* BFS 最短解求解器（状态指纹去重、`DIR_ORDER` 固定 ⇒ **同关同解**，可直接当断言用）；
* `generate(seed)`：模板 + 种子换手 + 撒尖刺，**由求解器把关**，同种子 byte 级一致；
* `tests/test_brickward.py` 30 项，其中 4 项是**已踩坑的回归守卫**（见 §9）。

### B1 阶段踩到的五个坑（都写进了回归守卫）

| # | 症状 | 根因 | 守卫 |
|---|------|------|------|
| 1 | 三关全"可解"，回放却全是穿模 | `doors` 一个集合既当"哪里有门"又当"哪扇门开着" ⇒ **关着的门能穿、开着的门挡人** | `test_closed_door_blocks_open_door_passes` |
| 2 | 拉杆关变成纯装饰 | `_settle` 查 `self.levers`（本意是"on 的集合"，装载后恒为空）⇒ 拉杆**从不翻转** | `test_lever_toggles_on_step` |
| 3 | BFS 搜出的解全是错的 | `clone_from` 里带 `_settle` ⇒ "人正站在拉杆上"的节点被克隆时把拉杆**扳回去** | `test_clone_does_not_retoggle_standing_lever` |
| 4 | 拉杆关"看起来能用"纯属巧合 | `_bind_links` 把三种事件全绑上，且 flip 处理函数**写死 `mode='toggle'`、无视连接声明的 mode** ⇒ `open` 连接每步"先开再翻回"，靠回调顺序抵销 | `test_link_modes_open_close_toggle` |
| 5 | `mode='close'` 的门永远堵死 | `src_on`/`src_off` 只在**变化**时发，"装载时本来就没触发"不算变化 ⇒ `close` 门等不到第一发 `src_off` | `test_link_modes_open_close_toggle` |

> 教训（值得写进下次的检查表）：**这几条全是"静默失效"** —— 不报错、测试还是绿的。
> 三条链路（`_cells` 静态格 / `*_cells` 与动态状态 / 连接订阅的事件类别）里，
> 任何"一个名字担两种含义"的地方都会长成这类 bug。B2 加新元素时先看这张表。


## 7. 与发行版的关系（吸取教训）

成片/附件的变更**一律攒批**到发布节点再一次性重建 release —— 因为 Gitee 附件**只能追加、
不能单独替换**，替换 = 删整个 release + 重传 362MB。
所以 B4 的成片与 boxward 视角改造后的 `boxward_60s.mp4` 都记在**待重建清单**里，等发布节点一起处理。
（本约定已同时写进 `docs/分发指南.md`。）
